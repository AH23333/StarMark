## 一、结论摘要

### 1.1 可行性结论

**MVP 完全可行**，且无阻断性技术障碍。核心风险集中在三处，均已在本文件中给出工程化解法：

1. **书签数据量导致的性能** → 分块遍历 + 事件增量构建索引，避免一次性 `getTree()`。
2. **MV3 Service Worker 生命周期** → 全部持久化 + 可恢复作业状态机，不做内存长驻。
3. **"像查书签一样快"的即时反馈** → 双查询路径（侧边栏全量模糊搜索 + 地址栏轻量前缀搜索），冷启动预算 ≤ 300ms。

### 1.2 技术选型一页速览

| 层 | 选型 | 版本 | 决策理由 | 备选（不采用的原因） |
|----|------|------|----------|----------------------|
| 扩展框架 | **WXT** | ^0.21 | 文件即入口、多浏览器构建、内置 sidepanel/background 支持、Vite 生态 | plasmo（sidebar 支持较弱）；纯手写 manifest（缺乏 DX） |
| UI框架 | **React + TypeScript** | 19.2 / 5.8 | 模板与生态成熟，`@wxt-dev/module-react` 官方支持 | Preact/Solid（生态小，收益低） |
| 本地存储 | **Dexie.js + IndexedDB** | ^4.2 | 突破 localStorage 5MB 限制；支持批量事务，SW 与页面共享 | SQLite (OPFS + sqlite3 wasm) —— 2026 年可用但复杂度高，MVP 不必要 |
| 全文搜索 | **MiniSearch** | ^7.2 | 内存索引"即搜即得"、可序列化持久化、支持模糊/前缀/字段加权 | FlexSearch（可更快，但无模糊匹配）；本地向量检索（Phase 3） |
| 认证 | **GitHub Fine-grained PAT** | — | 仅需 `Starring: Read` 用户权限，权限面最小 | OAuth（需后端换 token，MVP 不做，见风险）；Classic `public_repo`（权限偏大） |
| 状态管理 | **Zustand** | ^5 | 侧边栏局部状态，零样板 | Redux（过重） |
| 构建/测试/Lint | Vite(内置) + Vitest + ESLint9 | — | 与 WXT/Vite 同源 | — |
| 包管理器 | **npm**（本机 11.7 已装） | — | 一致性好 | pnpm（可后续切换） |

## 二、功能范围与系统边界

### 2.1 MVP 范围（做）

- 通过 PAT 拉取用户 GitHub Stars，本地缓存（含 starred_at 排序信息）
- 读取浏览器书签树并建立本地索引，订阅书签变更事件保持同步
- 侧边栏（Side Panel）+ 地址栏（omnibox 关键字）统一搜索，书签与 Stars 混排
- 结果卡片区分来源：书签显示域名/文件夹，Star 显示仓库名 + 语言 + Star 数
- 设置页（Options）：PAT 配置、同步频率、数据清空

### 2.2 边界（不做，列入后续）

| 能力 | 计划 | 备注 |
|------|------|------|
| AI 分类/标签、收藏理由记录 | Phase 2 | 需用户配置第三方 LLM Key |
| 语义/向量搜索 | Phase 3 | 本地嵌入模型或云端 API |
| 跨设备同步 | Phase 4 | 需后端或 Gist，涉及加密 |
| Firefox（无 Side Panel） | Phase 5 | 用 Popup 替代 |
| 取消 Star / 管理操作 | 前瞻 | 当前只读 |

## 三、系统架构

### 3.1 总体架构

```
┌────────────────────────────── 浏览器（Chrome/Edge, MV3）──────────────────────────────┐
│                                                                                        │
│  ┌─ Side Panel (侧边栏页面) ────────────────────────────────────────────────────────┐  │
│  │  React UI (Zustand 局部状态)                                                      │  │
│  │    ├─ SearchWorker(Web Worker): MiniSearch 索引构建/查询（不阻塞 UI）             │  │
│  │    └─ 直接读写 Dexie/IndexedDB                                                    │  │
│  └───────────────────────────────────────────────────────────────────────────────────┘  │
│                                                                                        │
│  ┌─ Options 设置页 ───────────────┐   ┌─ Background Service Worker（无长驻内存）──────┐  │
│  │  PAT 配置 / 同步管理 / 数据管理 │   │  · GitHubStarsSyncJob（可恢复状态机）        │  │
│  └───────────────────────────────┘   │  · 书签事件队列 → 增量 upsert                    │  │
│                                      │  · omnibox 地址栏轻量查询路径                     │  │
│                                      │  · chrome.alarms 定时同步                        │  │
│  ┌───────────────────────────────┐   └──────────────────────────────────────────────────┘  │
│  │ Omnibox（地址栏 "st 关键字"）  │                 ▲ 消息总线（typed messages）            │
│  └───────────────────────────────┘                 │ data flow    │ event broadcast       │
│                                                      ▼              ▼                       │
│  ┌───────────────────────── 共享核心层（core/，UI 与 SW 复用）────────────────────────┐   │
│  │  · 域类型 (types)   · URL 规范化/去重 (normalize)   · GitHub API 客户端 (api)       │   │
│  │  · Dexie schema (db)   · 消息协议 (msg)            · 工具 (utils)                   │   │
│  └───────────────────────────────────────────────────────────────────────────────────────┘   │
│  持久化：IndexedDB（items/searchIndex/syncState）+ chrome.storage.local（settings/token）    │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 职责划分原则

| 上下文 | 职责 | 禁止 |
|--------|------|------|
| **Side Panel**（常驻内存，打开期间存活） | 承载全部交互；持有 MiniSearch 索引副本（Worker 进程内）；直接读写 IDB | 不持有持久状态；不负责后台同步 |
| **Background SW**（随时可被杀） | 一切后台逻辑：GitHub 同步、书签事件、alarms、omnibox 应答 | ❌ 不允许持有内存长驻索引 / 长连接状态 |
| **Options 页** | 配置与诊断 | 不写业务数据 |

**关键决策：状态一律落 IndexedDB / chrome.storage.local，Side Panel 与 SW 都以 IDB 为唯一事实来源。** 这从根本上规避 MV3 SW 被终止导致丢状态的问题。

### 3.3 数据流

1. **Stars 全量同步**：`Options/首次安装 → SW 启动 SyncJob →/user/starred 分页拉取（带 If-None-Match）→ 写 items 表 → 对比 DB 计算已取消的 Star 并删除 → 标记 index 失效`。
2. **书签同步**：`安装时 + startUP 全量遍历一次 → 此后 onCreate/onRemoved/onChanged/onMoved 事件入队 → 1s 节流批量 upsert items 表`。
3. **查询（侧边栏）**：`击键 → SearchWorker.search()（索引内存态，~1-3ms）→ 命中 → UI 渲染。索引失效时后台重建，切到原生 chrome.bookmarks.search 兜底`。
4. **查询（地址栏）**：`用户输入 "st " 关键字 → SW onInputStarted 时从 IDB 拉起轻量建议列表(10k 条)入 SW 内存 → onInputChanged 逐次过滤返回 Top 8`。
5. **索引失效广播**：写 `chrome.storage.local` 的 `index:version` 计数器 + runtime message，Side Panel 监听后触发 Worker 重建。

## 四、技术选型确认（含论证）

### 4.1 认证方案：Fine-grained PAT（首选）

验证结论（2026-09 官方文档确认）：
- `GET /user/starred` 支持 **Fine-grained PAT，需 "Starring" 用户权限(Read)**，权限面远小于 Classic `public_repo`。
- 也支持 Classic `public_repo`（仅公开仓库）；若需包含私有仓库的 Star 才需要 `repo`，MVP 不推荐。
- **使用星光时间戳**：请求头 `Accept: application/vnd.github.star+json`，响应含 `starred_at`，用于排序与"最近 Star"展示。
- **条件请求**：若响应头含 `ETag`/`Last-Modified`，下次同步携带 `If-None-Match`/`If-Modified-Since`，命中返回 `304` 直接跳过全量比对。
- 速率限制：认证用户 5,000 req/h。按 100 条/页，1,000 Stars 全量约 = 10 请求，完全安全。

Token 安全：
- 存储于 `chrome.storage.local`（扩展隔离的持久存储，非全局 localStorage）。
- 扩展全局禁用 `eval`，CSP 收紧（`script-src 'self'`）。
- 禁止日志输出 token、禁止出现在错误上报中。
- 隐私政策明确声明：token 与数据仅存本地，不上传任何服务器。

### 4.2 数据模型（IndexedDB Schema，Dexie 定义）

```
db.version(1).stores({
  items:       'id, url, &url, title, sources, starredAt, bookmarkedAt, updatedAt',
  searchIndex: 'id, version, builtAt',            // 序列化 MiniSearch 索引，单条记录
  syncState:   'key',                             // key-value 作业检查点
})
```

**items 表（核心）** —— 键 = 规范化 URL 的 8 位十六进制 hash：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | `hash(normalizeUrl(url))`，书签与 Star 同 URL 合并为同一行 |
| `url` | string | 规范化后的 URL（见 4.3） |
| `title` | string | 展示标题 |
| `description` | string | 仓库描述 / 书签无则空 |
| `sources` | string[] | `['star'] / ['bookmark'] / ['bookmark','star']` |
| `starredAt` | number? | `starred_at` 时间戳 |
| `bookmarkedAt` | number? | 书签 `dateAdded` |
| `starMeta` | object? | `{ fullName, owner, repo, language, stars, topics[], archived, homepage, url }` |
| `bookmarkMeta` | object? | `{ folderPaths: string[], folderIds: string[] }` |
| `faviconUrl` | string? | `https://www.google.com/s2/favicons?domain=${host}` 兜底即可 |
| `createdAt / updatedAt` | number | 由同步管道维护 |

**syncState 表（可恢复作业检查点）** —— 键值对：

| key | 内容 |
|-----|------|
| `gh.sync` | `{ phase, page, starredCount, etag, lastModified, startedAt, doneAt }` |
| `bm.sync` | `{ lastFullWalkAt, pendingEventCount }` |
| `index.version` | 索引版本号（数据变更 +1） |

**chrome.storage.local（设置）**：
`{ pat, ghLogin, syncIntervalMinutes, omniboxEnabled, onboardedAt, privacyAcceptedAt }`

### 4.3 URL 规范化与去重规则

`normalizeUrl()`（`core/normalize.ts`）：
1. 补全协议（假设 `https`）。
2. 去除默认端口、尾随 `/`、`#fragment`。
3. host 转小写；剥离 `utm_*`、`fbclid`、`gclid` 等追踪参数。
4. GitHub 仓库页归一为 `https://github.com/{owner}/{repo}`。

效果：同一仓库既被 Star 又被收藏时合并为单条记录 `sources=['bookmark','star']`，结果卡片同时显示两种来源标记，天然去重。

### 4.4 搜索方案

| 查询面 | 数据规模 | 方案 | 延迟预算 |
|--------|---------|------|----------|
| 侧边栏 | ≤ 20,000 行 | **MiniSearch**：索引构建在 Web Worker，序列化索引持久化于 `searchIndex` 表；支持前缀 + 模糊(0.2)/字段加权（title 加权 2x，owner/repo 加权 1.5x）；增量 `add/removeById` | 查询 ≤ 5ms；索引恢复 ≤ 300ms |
| 地址栏（omnibox） | ≤ 20,000 行 | **轻量建议列表**：SW 会话内缓存 `[{id,title,url,sources}]` 到 `chrome.storage.session`；前缀 + 子串过滤取 Top 8（10k 条线性扫描 ~10-30ms） | 击键到建议 ≤ 50ms |
| 兜底 | — | 索引未就绪或构建中 → 侧边栏直接 `chrome.bookmarks.search(query)` 返回原生书签结果 | 即时 |

- MiniSearch 字段：索引 `title, url, description, owner, repo, topics`；`storeFields` 存储 `id, url, title, sources`。
- 索引版本策略：`index.version` 变化 → Worker 重建（增量事件被批量吸收后重建一次，节流 1s）。

### 4.5 混排与结果展示

- 分组展示优于纯分数混排（用户认知更清晰）：**命中段**（title/owner 精确或前缀匹配）> **通用段**（模糊匹配）。
- 段内按加权分降序；Star 与书签同 URL 合并为一行。
- 结果卡片：来源徽标（`⭐ Star` / `🔖 书签`）、标题、次级行（Star: `owner/repo · language · ★n`；书签: `域名 · 文件夹路径`）、快捷键打开新标签。

## 五、Manifest 与权限（wxt.config.ts）

```ts
export default defineConfig({
  srcDir: 'src',
  modules: ['@wxt-dev/module-react'],
  manifest: {
    name: 'StarMark',
    permissions: ['bookmarks', 'storage', 'sidePanel', 'alarms'],
    side_panel: { default_path: 'sidepanel.html' },
    omnibox: { keyword: 'st' },            // "st 关键词" 进入地址栏搜索
    action: { default_title: 'StarMark' },
    host_permissions: [],                  // 依赖 api.github.com 的 CORS(*)；若被拦截再补 https://api.github.com/*
    minimum_chrome_version: '114',         // sidePanel API
  },
})
```

权限最小化说明：
- `bookmarks`：核心（读取书签树）。商店审核时需在隐私说明中论证，且**只声明读取，绝不提供"修改书签"入口以降低风险**（事件监听只订阅，不改写）。
- `sidePanel`：打开侧边栏（WXT 检测 sidepanel 入口自动添加）。
- `alarms`：定时同步 Stars。
- **不加** `tabs`、`host_permissions`（MVP 不做网页注入），避免审核警告与权限扩散。
- `storage`：设置 + 索引版本计数器。

## 六、GitHub Stars 同步模块（`core/sync/github.ts`）

### 6.1 可恢复作业状态机（MV3 核心）

```ts
type SyncPhase = 'VALIDATE' | 'FETCH_PAGES' | 'RECONCILE' | 'TAG_INDEX' | 'DONE'
// 检查点字段写入 syncState['gh.sync']
```

每次作业从检查点恢复；SW 被杀后重启动依然从该 phase 继续，保证**幂等**（重复执行结果一致）。

1. `VALIDATE`：`GET /user` 校验 token → 401(失效)/403(权限不足)/200(写入 ghLogin)。
2. `FETCH_PAGES`：`GET /user/starred?per_page=100&page=N&sort=created&direction=desc`，`Accept: application/vnd.github.star+json`。
   - 首请求带 `If-None-Match`（上次 ETag）→ **304** 直接 `DONE`（未变化零成本）。
   - 逐页 `bulkPut` 到 items（每 500 条一批，避免大事务）；解析 `Link: rel="next"` 翻页。
   - 记录 `page` 检查点。
3. `RECONCILE`：拉全量后，对 DB 中 `sources includes 'star'` 但本次未见到的行 → 移除 `'star'`（若仍含 `'bookmark'` 则保留行，否则删除）。
4. `TAG_INDEX`：`index.version++`，广播失效通知。
5. `DONE`：写入 `doneAt`；创建下一次 `chrome.alarms`（默认 6h，`periodInMinutes` 用户可配）。

### 6.2 错误与重试

| 状态 | 含义 | 处理 |
|------|------|------|
| 401 / 403 | token 无效/权限不足 | 停止作业，Options 页标红，提示更换 token（附 Fine-grained `Starring: Read` 操作指引） |
| 429 / 5xx | 限流/服务端错误 | 指数退避重试（30s → 60s → 120s），记录到 `syncState`，下次 alarm 兜底 |
| 网络断 | — | 保留检查点，下次唤醒续跑 |

### 6.3 触发时机

- 首次完成 onboarding 后立即执行。
- `chrome.alarms`（默认 6h / 或按用户设置）。
- `chrome.runtime.onStartup` 若上次 `doneAt` 距今 > 设置间隔。
- Options 页"立即同步"按钮（手动）。

## 七、书签同步模块（`core/sync/bookmarks.ts`）

### 7.1 全量遍历（安装时 + onStartup 兜底）

- 不用 `getTree()`（万级书签一次性返回会卡顿、易触发 API 超时）。
- 分块 BFS：`getChildren(id)` 逐层，每批 200 节点 → `bulkPut`。
- 根节点解析：`getTree()` 只取根 → 递归其 children。**不依赖硬编码 ID**（Chrome `"0"`/Firefox `"root________"` 差异通过动态解析消除），同时对 W3C `ROOT_NODE_ID` 提案保持适配位。
- 用 `bookmarkMeta.folderPaths` 记录"书签栏/移动书签/具体文件夹"路径，供结果卡片展示。

### 7.2 增量事件（运行期）

- 订阅 `onCreated / onRemoved / onChanged / onMoved` → 写入内存队列 → **1s 节流**批量：
  - create/change：按 normalizedUrl upsert（update `'bookmark'` source / folderPaths）。
  - remove：仅移除 `'bookmark'` 来源标记，不误删同 URL 的 Star 行。
- 节流批量结束后 `index.version++` 并广播。
- SW 被杀期间丢失的事件通过"定期全量对账"兜底：`onStartup + alarms`（与 Stars 同步合并为一次对账任务）成本可控。

## 八、索引与搜索服务（`src/sidepanel/search-worker.ts`）

### 8.1 Worker 生命周期

```
DB(items) ──全量读(分块,懒加载)──▶ MiniSearch 实例 ──构造中--------▶ 就绪
                                     │                              │
                                     ├─ toJSON() 持久化到 searchIndex 表
                                     └─ 重建触发：index.version 变化 / 首次打开 / DB 升级
```

- 打开侧边栏时，Worker 拉起 `searchIndex` 序列化快照（10k 文档 ~1-3MB，恢复 ≤300ms）；无快照或版本过期则从 items 表重建。
- 增量接口 `upsert(items[]) / remove(ids[])` 供同步管道调用；写入后 `version++` 节流持久化。

### 8.2 查询接口（消息协议）

```ts
type SearchRequest  = { type:'search', q: string, max: number }
type SearchResponse = { id: string, url: string, title: string, sources: string[] }[]
// 字段加权 { title: 2, owner: 1.5, topics: 1.2 }, 前缀 + fuzzy 0.2, 分组混排见 4.5
```

## 九、消息总线与事件广播

- 统一 `core/msg.ts`，类型化消息（`SyncStart`、`SyncStateChange`、`IndexInvalidated`、`AuthInvalid`…）。
- 传播通道：`chrome.runtime.sendMessage`（定向）+ `chrome.storage.onChanged`（SW→页面 广播，index.version 由 storage 事件驱动，**不依赖 SW 存活**）。
- Side Panel 打开时主动拉取一次 `syncState` 快照对齐状态：

```ts
await runtime.sendMessage({ type:'GetState' })
```

## 十、MV3 生命周期策略（重要）

| 问题 | 策略 |
|------|------|
| SW 随时被杀 | 一切长期状态落 IDB/storage；作业带检查点可恢复；事件监听器在 `import` 顶层注册（每次唤醒重新挂载） |
| 不能在内存保留索引 | 索引归 Side Panel Worker 所有（Side Panel 打开期间存活）；SW 只留 omnibox 轻量建议缓存（按 indexVersion 失效，浏览器重启即清，天然无害） |
| 长任务拆解 | SyncJob 以"页"为单位分片，页间隔通过小 `setTimeout` 让出事件循环，防 30s SW 超时被杀 |
| SW 冷启动 | omnibox `onInputStarted` 提供一次"建建议缓存"的机会；对一切请求先用 checkpoint 判断是否需要恢复作业 |
| 运行时提前终止保护 | 作业每完成一页立即持久化 checkpoint；无需 `extension.isInIncognitoContext` 之类边界（本次不涉及） |
| **长任务消息模式（2026-09-17 定型，强制）** | **`runtime.sendMessage` 的响应通道撑不过长任务**（AI 流水线/批量分类/同步/全量遍历动辄数分钟，SW 生命周期终止或通道关闭 → "message channel closed before a response was received"）。所有耗时可能 >5s 的消息必须实现为：**同步建立 running 状态并落盘 → handler 立即返回 → 处理循环挂后台 promise**；UI 每 2s 轮询状态消息直到结束。任务循环内每条/每批的扩展 API 调用（storage/IDB 写入）会持续重置 SW idle 计时器保活。现役长消息：`ai-run` / `ai-classify-run` / `run-sync` / `walk-bookmarks`；参考实现 `core/ai/pipeline.ts`（runAiSuggestPipeline）与 `core/ai/classify.ts`（runClassify）。注意两点：① 启动语义必须由任务函数自己保证（状态落盘后才 return，handler 里 fire-and-forget 后紧接读状态会读到旧值）；② 任务函数必须有模块级防重入标志，运行中重复触发立即返回当前状态 |
| **同步防重入统一入口** | alarm/onStartup/onInstalled/PAT 变更等一切触发路径必须走 `guardedSync()`（内部 syncRunning 互斥），不允许直接调 `runGitHubSync` —— 多路径并发触发会竞态写同一份检查点 |

## 十七、AI 分类 / RAG 扩展预留（Phase 2/3）

当前架构已为 AI 自动分类与 RAG 语义检索留好扩展点，**以增量模块方式接入，不改变主架构**：

| 能力 | 现有基建复用 | 需新增（增量改动） |
|------|--------------|--------------------|
| AI 自动分类/标签/摘要 | `items.tags/summary/notes` 字段已预留；SyncJob 检查点模式直接复用于「AI 处理流水线」（可恢复、幂等、限流） | `core/ai/`（LLM Provider 抽象、批次调度、退避重试）；Options 页 API Key 配置与显式启用开关 |
| RAG / 语义检索 | `items.embedded` 字段预留；SearchWorker 内存态天然适合载入向量做余弦检索；双查询路径可融合「文本命中 + 向量召回」 | `embeddings` 向量存储（或 items 内联数组）；余弦计算放 Worker（20k 条 × 384 维 ≈ 30MB 内存，可接受）；索引升级到 v2 版本重建 |

关键设计约束（均已由当前架构满足）：

- **AI 与同步解耦**：AI 作业是独立的第二个 checkpoint 状态机，跑在 SW alarms 周期内；产物（tags/embeddings）与原始数据同级持久化，失败不影响搜索主链路。
- **LLM Provider 抽象**：`core/ai/provider.ts` 定义 `embed(text)` / `chat(messages)` 接口，OpenAI / Anthropic / 本地 Ollama 用适配器切换，用户只需改设置，不改代码。
- **API Key 存储**：与 PAT 同走 `chrome.storage.local`，设置页可一键清除。
- **索引版本演进**：索引以「版本号 + 序列化快照」定义（§8.1）；新增向量字段 → 索引 v2 重建即可，Side Panel 自动适配。
- **隐私政策双档**：纯本地模式与 AI 模式分开说明；AI 模式下条目标题/描述会按用户自配的 Key 发往第三方。设置页必须以显式开关开启 AI 模式，默认关闭。

### 17.1 已实现部分与实战经验（阶段 B / 2026-09，实现时踩坑沉淀）

Provider 抽象、建议流水线（检查点状态机 + 审核桶 suggestions 表 v4）、批量分类、Ollama 本地模型均已实现。以下是接入本地模型与运营 AI 流水线的实战经验：

**① 本地模型接入的三层关卡（缺一不可）**：

| 关卡 | 问题 | 对策 |
|------|------|------|
| 浏览器 CORS | 扩展跨域 fetch 本地服务被拦 | manifest `host_permissions` 覆盖服务地址（`localhost:11434/*`、`127.0.0.1/*`） |
| **服务端来源白名单** | Ollama ≥0.1.47 拒绝带 Origin 且不在白名单的请求（扩展 Origin 是 `chrome-extension://<id>`）→ **403 Forbidden**。host_permissions 管不了服务端拒绝 | 扩展后台用 declarativeNetRequest 动态规则移除"扩展自身（`initiatorDomains: [runtime.id]`）发往 localhost/127.0.0.1"请求的 Origin 头——Ollama 对无 Origin 请求不做校验，零配置放行；兜底指引用户设置 `OLLAMA_ORIGINS="*"` 后重启 Ollama |
| 地址歧义 | `localhost` 在部分环境解析为 IPv6 `::1`，Ollama 默认只监听 IPv4 `127.0.0.1` → 连接拒绝 | 默认/示例地址统一 `http://127.0.0.1:11434`；用户输入走 `normalizeOllamaBase` 校验（端口 1-65535、错误回显完整 URL） |

**② 长任务必须走"启动即返回 + 轮询"**：AI 流水线（逐条建议）与批量分类（50 条/批 × 最多 40 批）在本地模型下单条可达数十秒，绝不能在消息处理器里 await 完成（§10 长任务消息模式）。进度通过 `ai-review` / `ai-classify-state` 轮询；任务函数同步落盘 running 状态后立即返回。

**③ 标签碎片化对策**：逐条建议模式若只传条目自身标签，模型会为每个条目自创新词（表现为大量"一个标签只有一个条目"）。对策：流水线启动时取全库高频标签 top20（meta 直方图）作为 `globalTags` 进提示词，明确要求优先复用；批量分类同样用现有标签频次做【参考类别】锚定颗粒度。

**④ 配置检查必须统一**：`isAiConfigured()`（provider.ts）是唯一入口判断——Ollama 免 API Key，手写 `settings.apiKey` 判断曾在建议流水线漏掉豁免（另两处写对了），导致 Ollama 无法调用。

**⑤ 用户字段防丢**：AI 产物（tags/notes/summary/review*）全部在 `types.ts` 的 `USER_FIELDS` 白名单内，同步合并（mergePreserving）按白名单保留——新增 AI 字段时必须同步扩充白名单，否则下次同步静默清零。

新增 items 字段（Phase 2/3 冻结结构时启用）：`notes?: string`（收藏理由）、`summary?: string`、`tags?: string[]`、`embedded?: Float32Array`。

**结论**：MVP 的存储/索引/SW 恢复架构是上述能力的前置条件且已完备。

## 附录 A：GitHub API 要点（已核验）

- `GET /user/starred?per_page=100&page=N`：认证用户 Star 列表；支持 `Accept: application/vnd.github.star+json`（含 `starred_at`）；支持 `ETag`/`If-Modified-Since` 条件请求（304）。
- 认证要求：Fine-grained PAT **"Starring: Read"**（推荐）或 Classic **`public_repo`**（仅公开仓库）；含私有仓库需 `repo`（不推荐）。
- 速率限制：认证 5,000 req/h；缺省请求带 `X-RateLimit-*` 头，429 时读取 `Retry-After`。
- 分页：解析 `Link: <…page=2…>; rel="next"`。
