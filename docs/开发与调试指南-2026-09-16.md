## 一、环境准备与首次运行

```bash
# 前置：Node.js ≥ 20（wxt 0.21 要求），npm 随 Node 附带
cd D:\Visual Studio Code\Something\StarMark
npm install          # 首次会自动执行 wxt prepare（生成类型与 .output 骨架）

npm run dev          # 开发模式：构建到 .output/chrome-mv3-dev 并监视文件变化
```

加载到浏览器（Chrome/Edge ≥ 116）：

1. 打开 `chrome://extensions` → 右上角开启「开发者模式」
2. 「加载已解压的扩展程序」→ 选择 `.output/chrome-mv3-dev`（生产构建选 `.output/chrome-mv3`）
3. 固定工具栏图标 → 点击或 `Alt+S` 打开侧边栏

生产构建与发布包：

```bash
npm run build        # 产物 .output/chrome-mv3/
npm run zip          # 打包 .output/starmark-<ver>-chrome.zip（商店上传用）
```

**dev 与 build 的差异**：dev 模式带热重载（改代码后扩展自动 reload，SW 事件会重放）；建议功能验证最终以 `build` 产物为准。

## 二、三处调试入口（对应三个运行环境）

| 环境 | 怎么打开 DevTools | 能看什么 |
|---|---|---|
| **后台 Service Worker** | `chrome://extensions` → StarMark 卡片 → 「Service Worker」链接 | console、消息、同步日志；⚠ 关闭窗口 SW 可能被杀（可勾选卡片里的 dev 模式保活） |
| **侧边栏 / 设置页** | 页面上右键 → 检查（或 F12） | React 界面、与 worker/SW 的消息、IndexedDB |
| **搜索 Worker** | 侧边栏 DevTools → Sources → 页面树里的 worker；或 console 左上角下拉切换 context | `index`/`docCount` 内部状态（打断点看） |

**查看数据**：任一页面 DevTools → Application 标签 → IndexedDB → `starmark` 库（items/meta/…）；Storage → Extension → storage.local（pat/tagRules/indexVersion/…）。这是排查"数据到底写没写进去"的第一现场。

**常用 console 片段**（在侧边栏 DevTools）：

```js
// 看当前索引版本与补丁预案
chrome.storage.local.get(['indexVersion','idxPatch']).then(console.log)
// 看同步检查点
chrome.storage.local.get(['gh.sync','bm.sync']).then(console.log)
```

## 三、测试与类型检查

```bash
npm run test         # vitest 单测（纯函数：db 合并/备份/分词/规则/导出/分类解析…）
```

## 四、改一类需求要动哪些文件（修改路径地图）

### 4.1 加一个"后台动作"（如新增消息 `do-foo`）

1. `core/msg.ts`：`BgRequest` 加 `{ type: 'do-foo'; ... }`，`BgResponse` 加返回字段
2. `entrypoints/background.ts`：`onMessage` 路由加分支——**必须 `return true`**（否则异步 sendResponse 失效，这是最高频的新手坑）
3. 调用方（侧边栏/设置页）：`await sendToBackground({ type: 'do-foo' })`

### 4.2 给 `StarItem` 加一个用户可编辑字段

1. `core/types.ts`：字段加进 `StarItem`
2. **`core/db.ts` `mergePreserving`：加进用户字段保留清单**（漏了就会在下次同步被抹掉——审查报告 P0-2 正是这个坑）
3. `search-worker.ts` `docFromItem`：要可搜索就加进索引字段，要随命中返回就加进 `storeFields`
4. UI：`sidepanel/App.tsx` 卡片渲染 + 编辑入口；i18n 三语 key

### 4.3 加一个设置项

1. 选 storage key（保持全项目唯一——provider.ts 顶部注释记录了曾因占位 key 互踩的事故）
2. `options/App.tsx`：控件 + 读写 `storage.local`
3. 生效侧：多数设置 SW 在启动时读；若需要"改完立即生效"，在 `background.ts` 的 `storage.onChanged` 钩子里加分支（参考 `pat`/`lang` 的写法）

### 4.4 加一种自动标签规则类型

`core/rules.ts`：`RuleMatchType` 联合类型 + `ruleMatches` 分支；设置页规则编辑 UI 同步支持。

### 4.5 加一个 i18n 文案

`core/i18n.ts` 三个字典（zhCN/jaJP/enUS）各加同名 key；组件里 `t('your.key')`；带变量用 `t('k', { n: 3 })` + 模板 `{n}`。

### 4.6 改数据库结构

Dexie 是声明式版本：`db.ts` 里 `this.version(N+1).stores({...})` 追加新版本（旧版本签名保留不动），字段变更通常需要配合 `upgrade()` 回调做数据迁移。索引字段变化记得同步改 `search/indexer.ts` 并 `bumpIndexVersion()` 全量重建。

## 五、排查手册（症状 → 检查点）

| 症状 | 排查顺序 |
|---|---|
| **同步后搜索不到新 Star** | ① SW console 是否报错（限流/401）→ ② `gh.sync` 检查点 phase/error → ③ items 表里行存在？→ ④ `indexVersion` 是否递增、`idxPatch.ids` 是否包含新条目 → ⑤ worker 是否收到 invalidate（SW console 看 postMessage） |
| **计数（顶栏/标签云）不对** | meta 表 `app` 行 vs `items` 实际 count 对比；恢复过备份 → 审查 P0-1；手动修复可临时 `transformItems(()=>null)` 触发一次全量重算路径验证（根治需按审查建议做重算函数） |
| **编辑标签/笔记后界面没变** | worker 是否 ready（invalidate 后会广播）；`idxPatch.ids` 是否含该 id（审查 P1-3 的丢失场景） |
| **右键菜单没有「收藏到 StarMark」** | SW 是否存活（extensions 页 SW 链接点开看 console）；onInstalled 只在安装/更新时建菜单（审查 P1-4）；Chrome ≥ 116 |
| **Alt+S 无反应** | `chrome://extensions/shortcuts` 里检查快捷键是否被其它扩展抢占；background console 看 commands 事件 |
| **中文搜不到/搜不准** | indexer 的 CJK 分词只在**重建索引**时生效——改过分词器必须触发全量重建（`rebuild-index` 消息或 bump null 补丁） |
| **AI 报"未启用"** | `ai.settings` 是否真的写入（Application → storage.local 搜 `ai.settings`）；审查报告记录过 key 互踩史 |
| **扩展更新后数据消失** | 不会——IndexedDB 按 extension id 隔离持久保存；除非点了「清除数据」（它会连 Token/规则一起清，见审查 P2-4） |

## 六、推荐代码阅读顺序（第一周路线）

1. `core/types.ts`（30 分钟，把实体和消息协议过一遍）
2. `core/normalize.ts` → `core/db.ts`（主键怎么来、行怎么合并）
3. `core/sync/github.ts` 对照 [架构详解 §3](./架构与运行机制详解-2026-09-16.md) 状态机图走一遍
4. `core/version.ts` + `search-worker.ts` 对照 §2/§5（变更如何传播到索引）
5. `entrypoints/background.ts` 消息路由（所有入口的汇聚点）
6. 最后读 `sidepanel/App.tsx`（有了数据层认知后，UI 只是消费方）
7. AI 两个模块（pipeline/classify）与同步状态机对照着读，模式完全同构

调试练手任务建议（由易到难）：

- [ ] 在 SW console 手动触发 `run-sync` 并逐步打断点观察状态机迁移
- [ ] 修审查报告 P1-5（omnibox XML 转义）——改动 <10 行，有明确验收方式（搜含 `&` 的标题）
- [ ] 修审查报告 P0-2（mergePreserving 补 review 字段）——照 §4.2 地图，并补一条 vitest
- [ ] 加一个消息 `get-item`（按 id 返回单条）走通 §4.1 全流程

## 七、工程约束备忘

- **manifest 权限**（wxt.config.ts）：bookmarks/storage/sidePanel/alarms/contextMenus/declarativeNetRequest；host 权限 github.com（热榜抓取）、localhost:11434（Ollama）。加新能力若涉及新 API，先在这里加权限。
- **最低 Chrome 116**：sidePanel API 的底线；`sidePanel.close` 需 141，代码里已做能力检测降级。
- **没有 content script**：扩展不进入网页进程，所有能力围绕书签/存储/自有多页面。
- **`npm run compile` 必须过**：项目无 ESLint，类型检查就是主要的静态质量门。
- **CI**：仓库自带 vitest；提交前本地跑 `npm run test && npm run compile` 可覆盖绝大多数回归。
