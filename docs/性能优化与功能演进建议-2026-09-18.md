## 一、性能优化建议（按预期收益排序）

> 当前 5,000 条目级一切流畅；以下建议以"支撑 2 万条目 + 低端机"为目标，并给出验证方法。建议先做 **PER-0 打点基线**，其余项按数据决定优先级。

### PER-0 · 性能打点基线（先于一切优化）

**现状**：除同步耗时外无任何性能埋点，优化效果无法量化。
**方案**：`performance.now()` 埋 6 个关键点，写入 `storage.local.perf`（环形，保留最近 20 次），设置页诊断面板（DiagPanel）展示 P50/P95：
1. 侧边栏冷启动（`init` 消息 → `ready` 消息）
2. 快照加载 vs 全量重建耗时（worker `ensureIndex` 两分支分开记）
3. 首次搜索耗时（`search` 消息进 → `results` 出）
4. `applyPatch` 增量耗时与 ids 数量
5. `walkAllBookmarks` 总耗时与书签数
6. `runGitHubSync` 各 phase 耗时
**工作量**：半天 ｜ **风险**：无 ｜ 这是后续所有优化项的验收依据。

### PER-1 · 浏览模式卡片虚拟化（UI 最大热点）

**现状**：非搜索浏览模式 `max=500`，每张 ResultCard 约 40-60 个 DOM 节点，500 条 ≈ 2.5 万节点一次性 realize；滚动与输入防抖期间的主线程压力在低端机上可感知。
**方案**（两档，先 A 后 B）：
- **A. `React.memo(ResultCard)`**：props 仅有 `hit/query/prefs/onUpdate` 等，`onUpdate` 已是 `useCallback` 化的稳定引用——memo 后 query 不变的重渲染（如标签过滤切换、prefs 变更）全部跳过子树。预计浏览模式重渲染成本降 80%+。
- **B. 列表窗口化**：自实现简易虚拟滚动（`IntersectionObserver` + 上下缓冲各 10 条），替换 `visible.slice(0, shown)` 的"展开更多"模式——DOM 常驻 ~50 条，与数据量解耦。BrowseNode 树视图同理（每文件夹可视区外不挂载 ItemCard）。
**量化预期**：B 档后浏览模式 DOM 从 2.5 万 → ~3 千节点，滚动帧率稳定 60fps。
**涉及**：`sidepanel/App.tsx`（ResultCard 定义与列表渲染处）、`query.ts` 不变。
**工作量**：A 半天 / B 两天 ｜ **风险**：B 档需处理行高不定（描述折叠）——统一行高或先 `content-visibility: auto`（一行 CSS，收益约 6 成，可作为 B 的低成本替代先试）。

### PER-2 · 同步写库与对账的批量合并

**现状**：`runGitHubSync` FETCH_PAGES 每页 `upsertItems`（内部已分块事务，✅）；但 `reconcileStars` 里 `stripSourceForUrls(orphans)` 一次性传入全部孤儿 URL——该函数内部 `where('url').anyOf(urls)` 单次取行，OK；**真正的问题**：每页循环内 `await setSyncState(...)` 每页一次 storage 写 + `await sleep(0)`，200 页 = 200 次串行 storage 写。另 `logActivity` 每条新 Star 一次事务 + 一次 count 查询（500 上限修剪每次触发）。
**方案**：
1. 检查点改为**每 5 页**落一次（中间页丢失代价 = 重拉 ≤5 页，可接受）；或仅在 `phase` 变化与异常时落盘。
2. `logActivity` 改为收集后 `bulkAdd` + 修剪改"每 N 条触发一次"（而非每条触发 count）。
3. 新 Star 动态收集到数组，FETCH 结束后统一入库（对账同理）。
**量化预期**：万条 Star 全量同步的 storage 写次数从 ~400 降到 ~50；SW 存活压力同步下降。
**涉及**：`sync/github.ts`、`activity.ts` ｜ **工作量**：1 天 ｜ **风险**：低（检查点语义文档需同步更新：SW 被杀最多重拉 5 页）。

### PER-3 · 索引体积：CJK 二元组按字段分级

**现状**：`cjkAwareTokenize` 对**全部索引字段**（title/url/description/owner/topics/tags/notes）输出 整串+单字+二元组，中文描述较长的条目索引体积膨胀 2-3 倍，快照压缩后仍是内存与加载时长的主要构成。
**方案**：分词器按字段分级——`title/tags` 保留完整策略（它们短且是主要查询目标）；`description/notes` 只出**单字**（不出二元组与整串），二元组对长文本的查准贡献远低于体积成本。MiniSearch 的 tokenize 是全局单函数，可用 `fieldLength` 之外的技巧：在 `docFromItem` 阶段对长字段预截断（如 description 索引前 500 字符）——用户极少搜到 500 字以外的内容。
**量化预期**：快照体积 -30~40%（视中文描述占比），冷启动解压+反序列化等比下降。
**涉及**：`search/indexer.ts` ｜ **工作量**：半天 + 全量重建验证 ｜ **风险**：需 bump 索引版本强制重建；深文匹配召回略降（可接受）。

### PER-4 · GitHub 403/429 Retry-After 退避（正确性兼性能）

**现状**：`GitHubApiError.retryAfterMs` 已解析但同步循环直接终止；手动同步遇限流即失败，用户重试加剧限流。
**方案**：`runGitHubSync` 分页循环 catch `GitHubApiError`，若 `retryAfterMs` 存在且 ≤60s，`sleep` 后重试当前页一次（仅一次，二次失败照常终止并落 checkpoint.error）。alarm 周期同步遇限流直接放弃本轮（下轮自然恢复）。
**涉及**：`sync/github.ts`、`api/github.ts`（429 也解析 Retry-After）｜ **工作量**：半天 ｜ **风险**：低。

### PER-5 · activity 表修剪与查询索引

**现状**：修剪用 `orderBy('at').limit(count-500)` 取最旧再删，每次写都 count；`recentActivity` 走 `at` 索引 ✅。
**方案**：修剪改按龄清理：`where('at').below(Date.now()-90天).delete()`（Dexie 一次调用），count 检查降频为每 50 次写入一次。顺带把"500 条上限"策略改为"90 天 + 2000 条双上限"（动态页信息密度更高）。
**涉及**：`activity.ts`、`constants.ts` ｜ **工作量**：2 小时 ｜ **风险**：无。

### PER-6 · 杂项（各 ≤ 半天）

| 项 | 现状 | 建议 |
|---|---|---|
| omnibox XML 转义 | 标题含 `& <` 时建议渲染失败 | `formatOmniboxEntry` 前对 title/url 做 `&<>` 转义（审查 P1-5，仍未修） |
| favicon 网络请求 | 每个新域名一次 Google s2 请求 | 结果卡 IntersectionObserver 懒加载已有；补一个"离线模式"开关（UIPrefs），关后走首字母位（已支持） |
| `ensureSuggestCache` | 每次 onInputStarted 全表 `allItems()` | 改为仅 `title/url/sources` 三字段的投影查询（Dexie `items.toArray({title:1,...})`），或直接复用 worker 思路做 SW 侧小缓存（现有实现已带版本校验 ✅，只差投影减内存） |
| 快照双写 | 全量重建后同步写快照阻塞 ready 广播 | `persistSnapshot` 延迟到 ready 之后（现状 ensureIndex 内联写盘，大库重建时 ready 晚几百 ms） |
| `latest` 依赖 | `@wxt-dev/module-react: "latest"` | 锁到当前解析版本 + `package-lock` 提交（构建可复现，防上游 breaking） |

## 二、代码重构建议

### REC-1 · 响应类型同构（G1，重构路线已列）

`BgResponse` 是"全字段可选的大对象"，新增消息时漏填/错填字段编译期不报。改造为与 `BgRequest` 一一对应的判别联合：

```ts
type BgResponseMap = {
  'run-sync': { ok: boolean; error?: string }
  'get-state': { ok: boolean; state: BgState }
  'ai-review': { ok: boolean; ai: AiPipelineState; pending: TagSuggestion[] }
  // ...
}
type BgResponse = BgResponseMap[keyof BgResponseMap] & { ok: boolean; error?: string }
// sendToBackground 泛型化：<K extends BgRequest['type']>(req: {type: K} & ...)
//   → Promise<BgResponseMap[K]>，调用点自动获得精确返回类型
```

**收益**：15 个调用点的返回值全部强类型化（现在到处 `res.pending!`）。**工作量**：1 天（含 background 路由表化改造，见 REC-2）。

### REC-2 · background 消息路由表化

**现状**：`onMessage` 内 15 个 `if` 分支 + 手工 `return true`——新增消息忘写 `return true` 是 MV3 经典事故（通道提前关闭，调用方拿到 `undefined`）。
**方案**：

```ts
const handlers = {
  'run-sync': async (msg, send) => { ... },
  'get-state': async (msg, send) => { ... },
} satisfies { [K in BgRequest['type']]: Handler<K> }
// 统一：onMessage 里查表 → 存在则 void (async()=>{...})() 且 return true；不存在 return false
```

与 REC-1 同批落地，路由与类型一次收敛。**工作量**：与 REC-1 合计 1.5 天（纯移动，行为不变，用现有消息逐条对照）。

### REC-3 · 死代码与死权重清理

- `SearchDoc.description` 同时存在于索引字段与 docFromItem，但 storeFields 不含它、搜索 boost 也低——若采纳 PER-3 截断，顺带评估把 description 从 FIELDS 降级为可选配置。

## 三、功能扩展建议

> 与《功能点分级与实施路线.md》的关系：该文档已列出的 T1/T2/T3 不重复展开；此处给**新增项**与**已列项的落地设计细化**。每条标注复用的现有机制与工作量。

### F-1 ★ 与 StarMarkDesktop 桌面版互通（最高优先，双端联动独有优势）

**价值**：同一作者的桌面版（SQLite FTS5 + WinUI3）已具备更强的本地检索与组件能力；扩展作为"采集端 + 浏览器内快捷入口"，桌面版作为"重型管理端"，数据打通后形成产品矩阵。
**三步走**：
1. **导出桥（1 天）**：`export.ts` 加第四种格式 `starmark-desktop`——直接输出桌面版 `Item` JSON 结构（type/source/source_id/uri/tags/notes/hidden 映射已在桌面版 `ItemModel` 对齐过一轮）。设置页"导出到 StarMarkDesktop"按钮 → 下载 JSON → 桌面版设置页导入。**零新权限、零风险**。
2. **文件桥（2-3 天）**：导出同时写 `chrome.downloads` 到约定目录（如 `~/StarMark/export.json`），桌面版监听目录变更自动导入（桌面版加 FileSystemWatcher）。
3. **Native Messaging（远期）**：桌面版作为 NM 宿主，扩展实时推送收藏变更；桌面版反向提供深度检索。MV3 限制下走 `runtime.connectNative` 长连接，需桌面版安装时注册 manifest——列入 T3 观察项。
**复用**：`export.ts` 纯函数管线、`backup.ts` 加密信封（跨机传输时启用）。

### F-2 · 智能文件夹 / 保存搜索（T2 未列，性价比极高）

**设计**：侧边栏搜索态下"保存当前搜索"→ `{ id, name, query, tags, source, sort }` 存 `storage.local.smartFolders[]`；侧边栏顶部横向 chips 列出，点击即恢复完整查询上下文。规则标签（已有）+ 保存搜索（本项）= 轻量"动态视图"。
**涉及**：`App.tsx`（chips + 保存按钮）、`types.ts`（SmartFolder）、i18n 三语。
**工作量**：1 天 ｜ **风险**：无。

### F-3 · 去重合并工具（T1"自动去重增强"的落地细化）

**现状**：insights 已产出 `DuplicateGroup`（按标题/URL 判重），UI 只展示。
**设计**：健康报告的重复组 → 点击展开组内条目 → 勾选"保留 A"→"合并"：`tags/notes` 并集、`sources` 并集（若 URL 不同则保留 A 行 + B 行仅留 notes 摘要指向 A）。核心是 `db.ts` 新增 `mergeItems(keepId, dropId)`（一次事务 + applyItemDelta(old=drop, next=undefined) + meta）。
**工作量**：合并内核 1 天 + UI 1 天 ｜ **价值**：直接兑现"健康度→清理动作"闭环。

### F-4 · 回顾模式落地（schema 已备，纯增量）

`reviewedAt/reviewCount/reviewSkip` 字段与保留策略已就绪，只差 UI 与调度：
- **调度**：简化间隔重复——到期条件 `now - (reviewedAt ?? createdAt) > [1,3,7,14,30,60][min(reviewCount,5)] 天`；侧边栏第五个 tab「📖 回顾」，每次取 10 条到期条目，卡片三键：「记住了」(reviewCount++) / 「再看」(reviewedAt=now, reviewCount 不变) / 「不再提醒」(reviewSkip=true)。
- **入口逻辑**：`query.ts` 加 `dueForReview(items)` 纯函数（可单测）。
**工作量**：2 天 ｜ **复用**：StarItem 字段、ResultCard、worker tags 通道无关（直接 DB 查询即可，量小）。

### F-5 · 键盘导航（T2 已列，给键位表与实现要点）

侧边栏聚焦时：`j/k` 上下移动高亮条（复用现有 dup 高亮样式）、`Enter` 打开、`e` 编辑笔记、`t` 编辑标签、`h` 隐藏切换、`1-5` 切 tab、`/` 聚焦搜索框。实现要点：结果列表容器 `onKeyDown` + `data-index`，高亮索引存 `useState`（不用 focus，避免与输入框抢焦点）；命令面板（Ctrl+K）可后置——现有搜索框已是事实上的命令入口。
**工作量**：1 天 ｜ **风险**：低。

### F-6 · 阅读清单第三来源（SearchSourceRegistry 首个客户）

Chrome 120+ 的 `chrome.readingList` API（需加权限）。**触发 REC-6 一并实施**。同步逻辑与书签同构：全量 `getEntries()` + `onUpdated` 增量，条目映射为 `sources:['readinglist']`；阅读清单条目自带 `hasBeenRead/creationTime/lastUpdateTime`，正好喂给 F-4 回顾模式（未读条目优先复习）。
**工作量**：Registry 改造 1.5 天 + 来源实现 1 天。

### F-7 · GitHub Lists 双向同步（T2 已列，给状态机映射）

GitHub Lists 本质是"star + 一个 list 归属"。同步策略：Lists API（`/user/lists` + `/user/starred/{repo}/lists`?——以官方 GA 文档为准）拉取 `list.name → 条目集合`；与本地"标签 ↔ list"映射表（`storage.local.listMap: {tag: listId}`）对账。**关键决策**：单仓库可属多 list、单条目可多标签——映射天然相容；删除语义取"list 移除 ≠ 标签删除"（仅摘 list 映射），避免破坏本地标签。状态机复用 github.ts 的 checkpoint 模式（新增 `gh.lists` 检查点）。权限需 star:write 升级——放设置页显式开关，默认关。
**工作量**：3-4 天 ｜ **风险**：API 配额与 Token 权限升级，需在 UI 明示。

### F-8 · 标签别名与层级（T2"标签系统完整版"的轻量替代）

不做独立标签表（T2 完整版成本高），先做两个轻量能力：
- **别名归一**：`storage.local.tagAliases: {alias: canonical}`，`dedupeTags` 时映射（一处改动全局生效，含搜索索引——别名入库后索引天然归一）。
- **层级前缀**：标签名含 `/`（如 `ai/llm`）时标签云按前缀折叠展示一级（`ai (12)`），点击展开。纯 UI 分组，不改存储。
**工作量**：别名半天 + 层级 1 天。

### F-9 · 死链检测（谨慎项，默认关）

设置页手动触发：并发 5 的 HEAD 探测（4xx/超时标记 `deadAt` 时间戳，不自动删除），结果进健康报告"疑似失效"分组。隐私与流量明示。**工作量**：1.5 天 ｜ 放 T2 尾部。
