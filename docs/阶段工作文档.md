## 三、架构备忘（新会话必读）

- **长任务消息模式（2026-09-17 起强制）**：任何耗时可能 >5s 的消息（AI 流水线/批量分类/同步/全量遍历）必须实现为"**同步建立 running 状态并落盘 → 立即返回 → 处理循环挂后台 promise**"，UI 轮询状态消息直到结束。sendMessage 通道撑不过长任务，会报 "message channel closed"。现役长消息：ai-run / ai-classify-run / run-sync / walk-bookmarks，参考 `ai/pipeline.ts` / `ai/classify.ts` 的实现范式。
- **AI 配置检查统一走 `isAiConfigured()`**（core/ai/provider.ts）：Ollama 免 API Key，禁止手写 `settings.apiKey` 判断（已有三处不一致导致过两次线上故障）。
- **消息协议**：UI ↔ SW 走 `core/msg.ts` 的 `BgRequest/BgResponse`；`batch` 是唯一的写操作扩展点（`applyBatch`）。
- **索引失效链路**：任何 items 变更后必须 `bumpIndexVersion(ids)` → storage 事件 → 面板监听 → worker `invalidate`（ids 增量 / null 全量）。写代码时不要绕过这条链路。bump 已串行化（并发安全），面板侧有失效合并器。
- **meta 计数**：`items` 变更必须走 `upsertItems / updateItem / applyBatch / transformItems / stripSourceForUrls` 这些已维护计数的入口，不要直接 `db.items.put`。
- **用户字段白名单**：新增 StarItem 用户可编辑字段时必须同步加 `types.ts` 的 `USER_FIELDS`，否则同步合并/恢复会静默清掉该字段。
- **条目主键是 128-bit**（hashId，32 位 hex）：存量数据靠 Dexie v5 upgrade 自动迁移，不要用旧 id 格式写测试断言（8 位 hex 是旧格式）。
- **导出**：`buildExport(format, items)` 纯函数，items 用 `db.items.bulkGet(ids)` 或 `toArray()` 现取；UI 侧负责 Blob 下载。
- **规则存储**：`chrome.storage.local.tagRules`（用户配置，不是条目数据，不入 IndexedDB）。
- **本地模型接入三层关卡**（缺一不可）：① manifest host_permissions 覆盖服务地址；② 服务端来源白名单（Ollama ≥0.1.47 需 OLLAMA_ORIGINS，扩展已用 DNR 自动移除 Origin 绕过）；③ 地址用 127.0.0.1 显式回环（localhost 可能有 IPv6 歧义）。
- **测试环境**：vitest node + fake-indexeddb；依赖 `browser.*` 的代码路径在测试里要 mock `wxt/browser` 或绕开（如 `deleteBookmarks:false`）。后台任务型测试用轮询 helper（`runAndWait`，见 pipeline.test.ts）。

### 2.13 AI 长任务与 Ollama 对接修复（620bceb / 955deaa / 36adf92 / 86d838e）

- **根因 1（Ollama 免 Key 豁免漏网点）**：`runAiSuggestPipeline` 入口检查 `settings.apiKey` 未豁免 ollama——provider/classify 都写对了，唯独建议流水线主路径漏掉。**统一走 `isAiConfigured()`，禁止再手写 apiKey 判断**。
- **根因 2（Ollama 403 来源白名单）**：Ollama ≥0.1.47 对带 Origin 的请求做服务端白名单校验，扩展的 `chrome-extension://` Origin 不在默认名单 → 一律 403。host_permissions 只解决浏览器侧 CORS，管不了服务端拒绝。修复：后台 declarativeNetRequest 动态规则移除"扩展自身发往 localhost/127.0.0.1"请求的 Origin 头（`initiatorDomains: [runtime.id]` 严格限定，不碰浏览器其他请求）；403 报错附 OLLAMA_ORIGINS 修复指引。
- **默认地址 127.0.0.1:11434**：`localhost` 在部分环境解析为 IPv6 ::1 而 Ollama 默认只监听 IPv4。
- **MV3 长任务消息模式（关键架构决策）**：`sendMessage` 的响应通道撑不过长任务（SW 生命周期终止/通道关闭 → "message channel closed"报错）。ai-run / ai-classify-run / run-sync / walk-bookmarks 全部改为"**同步建立 running 状态并落盘后立即返回，处理循环挂后台 promise**"；UI 轮询状态消息直到 running=false（AI）或 syncing=false（同步，`BgState.syncing` 透出）。**新增任何耗时 >5s 的消息都必须走这个模式**。
- **启动竞态教训**：`void runTask()` fire-and-forget 后紧接着读状态，任务还没把 running=true 落盘 → UI 误判"瞬间完成"。启动语义必须由任务函数自己保证（状态落盘后才 return）。
- **全量跑完**：建议流水线 maxItems 默认 30 → Infinity（30 条/次是旧长任务时代的让出策略）；5000 Star 点一次跑完，每条检查点可续跑。
- **标签碎片化对策**：buildTagPrompt 新增 globalTags——启动时取全库高频标签 top20 进提示词，要求模型优先复用，缓解"一个标签一个条目"。
- 防重入：pipeline/classify 加模块级 active 标志，运行中重复触发立即返回当前状态。

### 2.14 AI 整理：abort 硬停止 + storage key 污染修复（ea698d9 / 1d3fc94）

用户实测反馈：任务被浏览器截断后模型仍在跑、无法暂停、两个 AI 按钮功能重叠。

- **重大 bug——storage key 占位符污染**：AI 域四个 key（AI 设置/建议流水线状态/分类结果/分类状态）的字面量全部是同一个占位符 `'***'`，互相覆盖——第一批分类落盘结果即冲掉 AI 设置（表现为"AI 未启用"/成果丢失）。拆分为 `ai.settings` / `ai.pipeline.state` / `ai.classify.result` / `ai.classify.state`。**教训：storage key 必须是有语义的真实字面量，code review 时对 `'***'` 之类的占位串零容忍。**
- **硬停止**：`provider.chat` 全链路支持 `AbortSignal`；`pauseClassify` 设置 `cancelRequested` 后**立即 abort 当前批次请求**——HTTP 连接即刻断开，本地 Ollama 检测到客户端断开会停止推理（不再把整批算完）。循环 catch 识别 `AbortError + cancelRequested` 落盘暂停态（被中断的批次不计入完成，续跑时重跑该批）。
- **双写竞态（测试抓出的生产 bug）**：pause 只写 storage 而循环读闭包内存 state → 暂停信号永远不可达。修复：**运行中状态以模块级共享单例对象（activeState）为唯一事实来源，storage 只是持久化镜像**；pauseClassify 不再自己落盘，等待循环落盘后返回（循环结束时 finally 置 activeState=null，等待循环必须用可选链读取）。
- **UI 合并**：移除逐条建议按钮与待审核列表，只保留单一「开始 AI 整理」入口（暂停/继续/断点续跑）；历史待审建议提供一次性清理按钮。逐条流水线代码保留但无 UI 入口（未来可作"仅补标无标签条目"选项回归）。
- 测试 117→118：批中 abort 中断回归（mock 模拟真实 signal 行为：**只挂第一批**，否则续跑批次永远挂起导致测试超时）、批边界暂停、僵尸解除。
