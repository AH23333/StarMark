## 一、这个项目是什么

StarMark 是一个 **Chrome 浏览器扩展**（Manifest V3），功能一句话概括：

> 把你的 **GitHub Stars** 和 **浏览器书签** 合并成一个本地数据库，提供统一搜索（侧边栏 + 地址栏 `st 关键词`）、标签管理、收藏夹树浏览、AI 自动打标签等能力。**所有数据只存在本机**（IndexedDB），GitHub 仅通过你自己的 PAT 只读拉取。

类比后端的话：它相当于一个"单用户、零运维、浏览器内嵌"的个人收藏检索服务——

| 后端世界的概念 | StarMark 里的对应物 |
|---|---|
| 应用服务器进程 | 后台 Service Worker（但会被浏览器随时杀掉，见 §三） |
| HTTP API 层 | `runtime.onMessage` 消息路由（`src/core/msg.ts` 定义协议） |
| MySQL/PostgreSQL | IndexedDB（浏览器内置的本地数据库），用 Dexie 库操作 |
| Redis 缓存 | `browser.storage.local`（键值存储，存配置和小状态） |
| Elasticsearch 倒排索引 | MiniSearch 内存索引（跑在 Web Worker 里） |
| 定时任务 cron | `browser.alarms`（最低 30 分钟粒度） |
| 前端页面 | 两个 React 页面：侧边栏（搜索主界面）+ 设置页 |
| 前端构建工具链 | WXT（扩展框架）+ Vite + TypeScript |

## 二、技术栈速成（只讲够用的）

### 2.1 TypeScript（.ts / .tsx）

JavaScript 加静态类型。`.tsx` 是"含 UI 模板的 TS"——模板叫 JSX，长这样：

```tsx
<button onClick={() => setTab('tree')}>文件夹</button>
```

它不是字符串拼接 HTML，而是声明"UI 长什么样"的表达式，编译后是函数调用。你可以在 `src/entrypoints/sidepanel/App.tsx` 里把它当成"用 XML 语法写 UI 组装代码"来读。

### 2.2 React（组件 + 状态驱动）

React 的核心模型一句话：**UI = f(state)**。你不手动改 DOM，只改状态（state），React 自动重算界面。

```tsx
const [query, setQuery] = useState('')   // 声明一个状态变量
// 任何地方 setQuery('rag') → React 自动重新执行组件函数 → 界面更新
```

项目里会反复见到四个钩子（hook）：

| Hook | 作用 | 后端类比 |
|---|---|---|
| `useState` | 组件内存里的可变状态 | 成员变量（但改它触发重渲染） |
| `useEffect(fn, deps)` | 状态变化/挂载时的副作用 | 事件监听器注册 + 生命周期回调 |
| `useMemo(fn, deps)` | 派生值缓存 | 带失效条件的 getter 缓存 |
| `useRef` | 不触发渲染的可变引用 | 普通成员变量（如 worker 句柄） |

`src/entrypoints/sidepanel/App.tsx` 顶部一大段 `useState` 就是整个侧边栏的"内存数据库"。

### 2.3 浏览器扩展的三种"进程"

一个扩展不是一个小网页，而是**三个隔离的运行环境**（互相不能直接调函数，只能发消息）：

```
┌─────────────────────────────────────────────────────┐
│  Background Service Worker（后台服务工，manifest 注册）  │
│  src/entrypoints/background.ts                        │
│  · 常驻"后台"：定时同步、消息路由、右键菜单、omnibox       │
│  · ⚠ 会被浏览器随时杀掉（空闲 30 秒），靠 storage 落盘续命 │
├─────────────────────────────────────────────────────┤
│  Side Panel（侧边栏，用户可见页面）                       │
│  src/entrypoints/sidepanel/  ← React 应用              │
│  · 搜索框、结果列表、收藏夹树、标签云、动态、隐藏页         │
├─────────────────────────────────────────────────────┤
│  Options（设置页，整页标签打开）                          │
│  src/entrypoints/options/    ← React 应用              │
│  · Token 配置、规则、AI、备份导入导出、健康报告            │
└─────────────────────────────────────────────────────┘
        ▲ 消息通信 runtime.sendMessage / onMessage ▲
```

还有一个隐藏的第四环境：**Web Worker**（`search-worker.ts`），由侧边栏创建，专职跑搜索索引，避免卡 UI 线程。

### 2.4 两套存储（容易混，务必分清）

| | IndexedDB（经 Dexie） | browser.storage.local |
|---|---|---|
| 定位 | **业务数据**（收藏条目、索引快照、动态、AI 建议桶） | **配置与游标**（Token、规则、AI 设置、indexVersion、同步检查点） |
| 形态 | 表 + 索引 + 事务，异步 API | 一个大 JSON 键值空间 |
| 类比 | MySQL | Redis + 配置中心 |
| 定义处 | `src/core/db.ts`（Dexie schema v1→v4） | 各模块自定义 key（如 `pat`、`tagRules`、`ai.settings`） |

`storage.session` 是第三个更小的：只在浏览器会话内存活的 KV（本项目存"哪些窗口开着侧边栏"）。

### 2.5 WXT（构建框架）

类似 Next.js 之于 React 网站：你按约定目录写代码（`entrypoints/background.ts`、`entrypoints/sidepanel/`…），`wxt.config.ts` 里声明 manifest（权限、快捷键、omnibox），它负责打包出 Chrome 可加载的 `dist/chrome-mv3/`。**本项目没有 content script**（不注入网页），权限清单见 `wxt.config.ts`。

## 三、一个必须建立的心智模型：Service Worker 会死

写过后端常驻进程的话，这是最反直觉的一点：

- 后台 SW **不是常驻进程**。浏览器空闲约 30 秒就把它杀掉；任何一个事件（闹钟、消息、书签变动）都会把它重新拉起、从头执行 `defineBackground` 回调。
- 所以 SW 里的**模块级变量全是易失的**。项目的对策遍布代码：
  - 同步进度 → 落 `syncState` 表（检查点状态机，被杀后续跑）
  - AI 流水线游标 → 落 `syncState`（每批/每条落盘）
  - 侧边栏开关窗口列表 → 落 `storage.session`
  - 书签增量事件队列 → 1 秒防抖批量处理 + 兜底全量对账（`maybeRestoreBookmarks`）
  - 索引版本 → `storage.local` 的 `indexVersion`（UI 据此感知数据变化）

读代码时看到"先读状态、处理、再写回状态"的循环，都是在跟"SW 随时会死"搏斗。

## 五、核心实体：一行数据的一生

整个系统围绕一条记录转动——`StarItem`（`src/core/types.ts:26`）：

```ts
{
  id: 'a3f9c2d1',          // = hashId(normalizeUrl(url))，8位十六进制
  url: 'https://github.com/x/y',
  title: 'x/y',
  description: '...',
  sources: ['star', 'bookmark'],  // ★ 同一 URL 的 Star 和书签合并成一行
  starredAt: 1700000000,    // 何时加的 Star
  bookmarkedAt: 1710000000, // 何时收藏的书签
  starMeta: { language, stars, topics, ... },     // GitHub 元信息
  bookmarkMeta: { folderPaths: ['工具','搜索'], ... }, // 书签目录路径
  tags: ['ai','工具'],       // 用户/规则/AI(批准后) 维护
  notes: '备用',             // 用户笔记
  hidden: true,             // 隐藏标记
  createdAt / updatedAt,
}
```

两个设计要点：

1. **主键 = URL 哈希**：同一条 URL 无论从 Star 还是书签来，都落到同一行（`sources` 数组记录来源），删除某一来源只"摘源"不清行（`stripSourceForUrls`）。
2. **meta 缓存表**：`meta` 表存着 total/stars/bookmarks/标签直方图等聚合计数，每次行变更用 `applyItemDelta` 做增量 ±1（见 `db.ts:84-116`），避免每次打开面板全表扫描。

## 六、五个"用户动作"的完整旅程（先建立直觉）

细节都在下一篇文档，这里先给直觉：

1. **点「同步」**：侧边栏发消息 `run-sync` → SW 跑 GitHub 同步状态机（拉 starred 分页 → 合并入库 → 对账删除）→ `bumpIndexVersion` → 侧边栏监听到版本变化 → 通知 Worker 增量更新索引 → 界面刷新。
2. **输入搜索词 "rag"**：侧边栏 120ms 防抖 → 发给 Worker → Worker 用 MiniSearch 查内存索引（+全表字面兜底）→ 返回命中 → 界面分组渲染。
3. **编辑一条的标签**：侧边栏发 `update-item` → SW `updateItem`（事务内改行 + 增量改 meta）→ bump 版本（带该条 id）→ Worker 增量补丁该条 → 完成。
4. **在网页上右键「收藏到 StarMark」**：SW 收到 contextMenus 点击 → 在书签栏建「StarMark 收藏」文件夹并写入书签 → 浏览器触发 `bookmarks.onCreated` → 书签增量队列 1 秒后批量入库 → 自动打规则标签。
5. **地址栏输入 `st rag`**：omnibox 事件 → SW 内存建议缓存（带版本校验）→ 打分排序返回前 8 条 → 回车开新标签页。
