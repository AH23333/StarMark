## 二、Bug 清单（按严重度）

### P0 —— 数据丢失 / 数据错乱

**P0-1 · 恢复备份后 meta 计数错乱、AI 建议与动态残留**
- 位置：`src/core/backup.ts:96-100`（`restoreBackup`）、`src/core/db.ts:176-193`（`upsertItems`）
- 现象：`restoreBackup` 只 `db.items.clear()` 后调用 `upsertItems`。meta 表的旧计数（total/stars/bookmarks/tags 直方图）**未被重置**，`upsertItems` 又按"新增"逐条 `+1`，结果 `total = 旧计数 + 导入条数`，顶栏与标签云计数全部翻倍/错乱。
- 同时 `suggestions`（AI 建议桶）与 `activity` 表**未清空**，指向已不存在条目的悬空建议会继续显示。
- 修复建议：提供一个从条目全量重算的 `computeAppMeta(items)`；`restoreBackup` 在同一事务内 `items/suggestions/activity` 三表 clear + 重写 meta 基线 + bulkPut，最后 `bumpIndexVersion()`。

**P0-2 · 同步覆盖"回顾模式"字段（reviewedAt/reviewCount/reviewSkip 丢失）**
- 位置：`src/core/db.ts:161-174`（`mergePreserving`）
- 现象：合并策略显式保留 `tags/notes/summary/hidden/embedded/createdAt`，但 `reviewedAt / reviewCount / reviewSkip`（types.ts:46-49，回顾模式）不在保留清单里。`repoToItem` 产物不含这些字段，`{...incoming}` 展开即丢弃 → **每次 GitHub 同步/书签增量都会把用户的回顾进度清零**。
- 修复建议：`mergePreserving` 补上 `reviewedAt: old.reviewedAt, reviewCount: old.reviewCount, reviewSkip: old.reviewSkip`（或改为"用户维护字段白名单"统一维护，防再犯）。
- 测试：`db.test.ts` 补一条"upsert 后 review 字段保留"。

### P1 —— 正确性

**P1-1 · 条目主键 32-bit 哈希存在碰撞风险（大规模下互相覆盖）**
- 位置：`src/core/normalize.ts:55-63`（`hashId`）
- 现象：id = FNV-1a 32-bit（8 位 hex）。生日碰撞在约 7.7 万条时概率过半；1 万条时约 2.3%。碰撞时两条不同 URL 共享主键，`bulkPut` 静默用后写覆盖前写（`&url` 唯一索引拦不住同 id 异 url），**无任何报错的数据丢失**。
- 修复建议：Dexie v5 迁移，将 id 扩为 128-bit（如 crypto.subtle SHA-256 截断 16 字节 hex，或双哈希拼接）。迁移期按 url 重算 id 做一次性改写。

**P1-2 · ETag 增量轮询实际失效，定时同步退化为全量爬取**
- 位置：`src/core/sync/github.ts:99-109`（循环内保存 etag）、`:37-44`（DONE → FETCH_PAGES 复用 etag）
- 现象：ETag 是"每页表示"的指纹，而检查点保存的是**上一轮最后一页**的 etag；下一轮把它用在 page=1 上必然 200 → 循环内每页又带着上一页的 etag 请求下一页，也必然 200 → **每个 6h 周期任务都做全量 N 页爬取 + 全量 DB 写**（正确性靠 `mergePreserving` 兜底，但白白消耗 API 配额与 SW 生命周期）。
- 修复建议：只在 page=1 携带 If-None-Match（新 Star 只会出现在第一页），命中 304 直接结束；未命中时后续页**不带**条件头。或者接受全量爬取、删掉 304 相关代码以免误导。

**P1-3 · `bumpIndexVersion` 读改写竞态，可能丢失增量补丁**
- 位置：`src/core/version.ts:18-24`
- 现象：`getIndexVersion()+1 → set` 非原子。`runGitHubSync` 结束时的 `bumpIndexVersion([...changed])` 与 `finish()` 里 fire-and-forget 的 `applyRulesToAll()` 内部的 bump 极易相邻发生；丢失更新时两次写同一版本号，后一个 `idxPatch` 覆盖前一个 → **前一批变更 id 的索引补丁永久丢失**，搜索结果停留在旧数据，直到某次全量重建。
- 修复建议：用单条 `browser.storage.local.set` 传入自增逻辑不可行，可改为：把补丁 id 追加进一个队列 key（`idxPatchQueue`，读-改-写放同一 `storage.local` 的 set 由调用方串行化——SW 内已有 `syncRunning` 互斥，但 rules/bookmarks 路径没有），或干脆让 worker 收到任意版本变化即做"按 id 增量 + 定期全量"的兜底（现状已有 `ids>=docCount/2 全量重建`，可再加"worker 收到 invalidate 时对上一版本差集重放"）。最小修复：所有 bump 收敛到一个模块级 Promise 链串行化（SW 单线程内足够）。

**P1-4 · 右键菜单重复创建报错**
- 位置：`src/entrypoints/background.ts:117-125`
- 现象：`onInstalled` 在**更新**时也会触发，而 Chrome 的 contextMenus 在 SW 重启/更新后仍保留；`contextMenus.create({ id: 'starmark-collect' })` 重复创建会 reject（`Cannot create item with duplicate id`），且该 promise 未接 `.catch` → 未处理 rejection。
- 修复建议：`await browser.contextMenus.removeAll()` 后再 create（或 create 包 try/catch，或检查 `runtime.getLastError`）。

**P1-5 · omnibox 建议未做 XML 转义**
- 位置：`src/entrypoints/background.ts:101-104`（`formatOmniboxEntry`）
- 现象：Chrome 建议描述是 XML 语法，标题/URL 直接内插。含 `<`、`&` 的标题（`vector<int>`、`C & C++` 类仓库很常见）会导致该条建议渲染失败或内容缺失。
- 修复建议：对 title/url 做 `& < >` 转义后再拼 `<url>/<dim>` 标记。

**P1-6 · 后台 SW 未调用 `initI18n()`，显式语言偏好在 SW 内不生效**
- 位置：`src/entrypoints/background.ts`（仅 `changes.lang` 时调用）、`src/core/i18n.ts:948`
- 现象：`lang` 初始值取浏览器 UI 语言；用户显式选择的语言只有在下一次 `changes.lang` 事件时才会应用。SW 重启后右键菜单标题回退到浏览器语言而非用户选择。
- 修复建议：`defineBackground` 回调开头 `void initI18n()`。

**P1-7 · 书签 moved/changed 事件使用占位路径 `['']`**
- 位置：`src/core/sync/bookmarks.ts:169-180`（`changedOrMoved` 分支）
- 现象：`onMoved/onChanged` 直接以 `folderPaths: ['']` upsert——移动/改名后的书签在收藏夹树上**错位到根**，直到下一次全量遍历（10 分钟节流，最长可能 1 小时）才纠正。`created` 分支已有 `folderPathFor(parentId)` 即时回溯路径，此处应复用。
- 修复建议：`changedOrMoved` 拿到 `node.parentId` 后同样调用 `folderPathFor`。

### P2 —— 健壮性 / 体验

**P2-1 · 全量书签遍历：N+1 且检查点写在开头**
- 位置：`src/core/sync/bookmarks.ts:63-92`
- 现象：每个书签一次 `getByUrl` + 一次独立 `upsertItems` 事务（每条各读写一次 meta），1000 书签 ≈ 数千次 IndexedDB 事务；且 `lastFullWalkAt` 在**遍历开始**就写入，SW 中途被杀会留下"半截数据 + 新鲜时间戳"，10 分钟内不会重走 → 书签可能长期缺失。
- 修复建议：BFS 先收集全部节点 → 一次 `bulkGet` 合并 → 单事务 `bulkPut`（对齐 `upsertItems` 的分块模式）；`lastFullWalkAt` 移到遍历成功后写入（或写"进行中代次"标记）。

**P2-2 · 搜索字面兜底每次全表加载**
- 位置：`src/entrypoints/sidepanel/search-worker.ts:209-220`
- 现象：MiniSearch 命中不足 max 时，每次按键（120ms 防抖后）都 `allItems()` 全表加载 + 线性扫描。5000+ 条目、连续输入时 worker 压力明显。
- 修复建议：仿照 `background.ts` 的 `suggestCache`——worker 内维护带 indexVersion 校验的全量缓存；或兜底扫描仅对 MiniSearch 未命中的补充集合执行。

**P2-3 · 动态表修剪的并发竞态**
- 位置：`src/core/activity.ts:5-13`
- 现象：`count()` 后按差值删除最旧记录，并发写入时可能略超 500 条（无实际危害，仅体积）。同步循环内多处 `void logActivity(...)` fire-and-forget，SW 被杀会丢个别动态（可接受，建议注释说明）。
- 修复建议：修剪改为 `where('at').below(Date.now() - N天)` 按龄清理，或容忍误差。

**P2-4 · `clearAll` 连同 Token/规则/偏好一并清除**
- 位置：`src/core/db.ts:414-418`
- 现象：`browser.storage.local.clear()` 会清掉 pat、tagRules、UIPrefs、语言。设置页文案为"清空所有数据"——若意图仅是清条目，应只清 DB + indexVersion；若确要全清，确认弹窗应明确列出"包括 Token 与规则"。

**P2-5 · 403 Retry-After 未被利用**
- 位置：`src/core/api/github.ts:39-42`、`src/core/sync/github.ts:142-146`
- 现象：`GitHubApiError.retryAfterMs` 已解析但同步层收到 RATE_LIMITED 直接结束，无退避重试。周任务场景影响小，手动"保存并同步"场景体验差。
- 修复建议：同步循环内对 403/429 做 1 次 `sleep(retryAfterMs)` 重试。

**P2-6 · 备份 Base64 逐字节拼接**
- 位置：`src/core/backup.ts:14-25`
- 现象：`bin += String.fromCharCode(b)` 对 MB 级密文产生大量中间串。改为 8KB 分块 `String.fromCharCode.apply` 或 `FileReader.readAsDataURL`。

**P2-7 · 依赖版本 `"latest"`**
- 位置：`package.json`（`@wxt-dev/module-react`）
- 现象：构建不可复现，上游 breaking change 会直接破坏 CI。锁定到具体版本。

### 设计确认项（非 bug，建议明确）

- **PAT 明文存 `storage.local`**：扩展生态常规做法；README 已推荐 fine-grained 只读 Token，建议再加一句"Token 与数据均不离开本机"的安全说明。
- **favicon 走 Google s2 服务**：每个新域名会向第三方发起一次请求（暴露浏览足迹）。可选：设置项关闭 favicon 或改用 `chrome://favicon/`。
- **`doSearch` 返回 `total: out.length`**：语义是"本次返回条数"而非命中总数，UI 若显示"共 N 条"会误导。

## 四、重构优化点

**R1 · 巨石 UI 文件拆分（优先）**
`sidepanel/App.tsx` 1581 行、`options/App.tsx` 952 行。至少拆出：
- `sidepanel/components/ResultCard.tsx`、`BrowseNode.tsx`、`ContextMenu.tsx`、`ActivityRow.tsx`（文件内已有清晰分界）
- `core/ui-utils.ts`：`relativeTime / tagColor / highlight / escapeHtml / safeHost / hostOnly`（目前全部内联在 App.tsx）

**R2 · 排序比较器三处重复**
`search-worker.ts:sortItems`、`search/selectors.ts:sortByPref`、`sidepanel/App.tsx:sortHits` 语义相同。统一到 `selectors.ts` 一处（worker 与 UI 共享 import，注意 selectors 目前 import 自 insights，无循环风险）。

**R3 · background 消息路由表化**
`onMessage` 里 15 个 `if (msg.type === ...)` 分支 + 手工 `return true`。改为 `const handlers: { [K in BgRequest['type']]: Handler }` 映射，统一异步包装与错误响应，降低"忘写 return true 导致 sendResponse 失效"这类隐患（现在靠约定维持，易在新增消息时出错）。

**R4 · 死代码清理**
`normalize.ts:sortByStars`、`api/mappers.ts:mergedWithBookmark` 无任何调用点。删除或补用途。

**R5 · i18n 词典外置**
`i18n.ts` 1021 行内嵌三语字典。拆为 `locales/zh-CN.json` 等三份资源（wxt 支持 JSON import），`i18n.ts` 只留逻辑（~120 行）。收益：翻译维护、PR diff 可读性。

**R6 · worker 全量数据缓存**
见 P2-2；顺带让 `buildFolderTree` 与兜底扫描共享同一缓存。

**R7 · 上下文复用 `ItemEditPatch` 白名单**
`mergePreserving`（P0-2 根因）与 `updateItem` 各自维护"用户字段"清单。提取 `const USER_FIELDS = ['tags','notes','summary','hidden','embedded','reviewedAt','reviewCount','reviewSkip'] as const`，merge 与测试共用，防新增字段再次漏保。

### 性能优化

| # | 优化 | 收益 | 落点 |
|---|---|---|---|
| O1 | **书签树直读**：`walkAllBookmarks` 直接遍历 `getTree` 返回的完整树（节点自带 children），不再逐层 `getChildren` | 几百个目录 = 几百次 bookmarks IPC → **1 次 API 调用 + 纯内存遍历** | `core/sync/bookmarks.ts` |
