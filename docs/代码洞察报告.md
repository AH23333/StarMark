## 二、按模块洞察

### A. 数据层 `core/db.ts`（557 行）

**现状**：Dexie 定义（v1–v6 迁移）+ items CRUD + meta 计数 + 批量操作 + 建议桶 DAO + `getSyncState/setSyncState`（syncState 表的 KV 封装）全部在一个文件。

**问题**：
- **A1 · 职责过载**。schema/迁移是一回事，`applyBatch`/`approveSuggestions` 这类业务写入是另一回事，混在一个 557 行文件里，新人定位成本高。
- **A2 · 迁移链已 6 版**。v1→v6 每次打开都要顺序声明；其中 v5/v6 都做了"清表重建 + 重映射"，属一次性修复型迁移。
- **A3 · `CHUNK = 500` 魔法数在本文件出现 2 次，在 `sync/bookmarks.ts`、`search-worker.ts` 又各 1 次**，语义相同（bulkPut 分块）但互不相干，改一处漏三处。
- **A4 · `getSyncState/setSyncState` 是通用 KV 封装，却定义在 db.ts**，被 sync/ai/background 多处使用——它其实是独立的"作业状态仓库"概念。

**建议**：
1. 拆 `core/db/schema.ts`（Dexie 定义 + 迁移链）与 `core/db/items.ts`（CRUD/meta/batch）；`getSyncState/setSyncState` 迁至 `core/job-state.ts`。db.ts 保留 re-export 以免调用方破坏（P2）。
2. `CHUNK = 500` 收敛到 `core/constants.ts`：`DB_BULK_CHUNK`、`AI_BATCH_SIZE`、`WORKER_CHUNK` 分开命名，语义各自独立（P3）。
3. 未来 v7 迁移建议**做基线压缩**：v7 里检测 `meta.schemaBaseline >= 7` 则跳过 v1–v6 逻辑，把整段迁移历史折叠为一次幂等重建（P3，当前用户量小不急）。

### B. 同步层 `core/sync/github.ts` + `core/sync/bookmarks.ts`（195 / 293 行）

**现状**：状态机检查点模式，可恢复、幂等；书签侧已做 getTree 直读、批内共享树、批量入库。

**问题**：
- **B1 · `github.ts` 与 `bookmarks.ts` 是两套风格相近但不共享骨架的状态机**（checkpoint 读写、防重入、sleep 让出、错误落盘各自实现）。下次再增加作业（如 Lists 同步、向量索引作业）会第三次复制。
- **B2 · `bookmarks.ts` 的 `flushTimer` 1s 节流与 `applyOps` 状态是模块级单例**，SW 重启即丢——丢失的是 1s 窗口内的事件，由 10 分钟节流的全量遍历兜底，可接受但**没有注释说明这个兜底关系**，未来改动易破坏不变量。
- **B3 · 事件→操作映射（onChanged/onMoved → changedOrMoved）与 op 处理耦合在一个 `applyOps`**，新增书签事件类型（如 `onChildrenReordered`）需要同时改两处。

**建议**：
1. 抽 `core/sync/job-runner.ts`：封装"防重入 + checkpoint 读写 + sleep(0) 让出 + 错误落盘"的通用骨架，github/bookmarks 变为声明式步骤（P2）。
2. `bookmarks.ts` 顶部补一条不变量注释："事件丢失由 10 分钟节流全量遍历兜底，因此 1s 节流窗口可容忍"（P3，纯注释）。
3. op 处理改为 per-kind 处理器表（与 background 消息路由表同风格）（P3）。

### C. AI 层 `core/ai/*`（provider 310 / classify 479 / pipeline ~200 行）

**现状**：Provider 抽象良好（新增厂商 = provider.ts 加一个 chat 函数）；classify/pipeline 是两个独立作业状态机；abort 心跳/防重入/检查点齐备。

**问题**：
- **C1 · 中文文案散落最严重的模块**：`provider.ts`（buildTagPrompt 提示词、Ollama 403 指引等 8 处）、`classify.ts`（buildClassifyPrompt、'AI 未启用'等 6 处）、`api/github.ts`（错误消息 10 处）、`backup.ts`（4 处）、`convert.ts`（4 处）、`db.ts`/`trending.ts`（各 1–2 处）。**这些字符串最终会以 toast 形式直达用户**——非中文用户看到中文报错。
- **C2 · `classify.ts` 一个文件四种职责**：状态机 + prompt 构建（buildClassifyPrompt）+ 响应解析（parseClassifyResponse）+ 分组推导与导入导出 DAO。
- **C3 · pipeline 与 classify 的状态机再次相似**（startedAt/doneAt/error/running + 检查点 + 防重入 + lastBeatAt/cancelRequested）——与 B1 同病：缺一个通用"可暂停作业"骨架。
- **C4 · 错误类型是裸 `Error` + 字符串**，UI 无法程序化区分"配置错误 / 限流 / 网络中断 / 用户中止"，只能靠文案匹配。

**建议**：
1. 新增 `core/ai/prompts.ts` 集中全部提示词模板（入参化），用户可见的**错误消息**迁移进 locales（错误 key 化：`{ ok:false, errorKey, errorVars }` 或 Error 子类携带 i18n key）——一步到位成本高，可先做 Error 子类：`AiConfigError / AiRateLimitError / AiAbortError`，UI 按 error.name 走 i18n（P2）。
2. classify.ts 拆三件：`classify/machine.ts`（状态机）、`classify/prompt.ts`（构建+解析）、`classify/dao.ts`（result 存取/导入导出）（P2）。
3. 吸收 B1 的 job-runner 后，pipeline/classify 的公共骨架（心跳/暂停/防重入/检查点）收敛为一个 `createLongTask()` 工厂（P2，与 B1 合并实施）。

### D. 索引与搜索 `core/search/*` + `search-worker.ts`（368 行）

**现状**：版本化全量缓存、增量补丁、快照持久化（4s 防抖）、CJK 分词，热路径已充分优化。

**问题**：
- **D1 · worker 内 `doSearch`/`buildFolderTree`/`applyPatch` 无单测**——逻辑在 worker 上下文里，现有测试只能覆盖 core 层；这些是结果正确性的核心路径（过滤/排序/查重/树构建）。
- **D2 · `sortItems` 语义统一后，worker 与 UI 共享 `selectors.ts` ✓；但**过滤逻辑**（keep/hasTags）仍在 doSearch 内联，BrowseNode 的过滤（prefs.showHidden / languageFilter）又是另一份——来源/隐藏/标签三类过滤的判定散落两处。
- **D3 · 兜底扫描的 `out.length >= max` 提前退出依赖遍历顺序**（缓存数组的插入序），不是排序后的前 N——功能正确但截断的条目选择不稳定。
- **D4 · 快照持久化用 `compressText`（CompressionStream）**，Safari/Firefox 适配时需 feature-detect（已有 `hasDeflate` ✓），但**快照无版本头**——分词器或 schema 升级后旧快照 loadJSON 可能抛错（当前靠 try/catch 兜底全量重建 ✓，可接受）。

**建议**：
1. 把 doSearch 的**纯逻辑部分抽成 `core/search/query.ts` 纯函数**（输入 items/参数，输出 hits）——worker 只剩消息分发与 MiniSearch 调用，core 测试直接覆盖（P2，收益最高的一条）。
2. 过滤谓词收敛到 `core/search/filters.ts`（source/hidden/tags/language 各一个谓词工厂），worker 与 BrowseNode 共用（P2，随 1 一起做）。
3. 快照头部加 `{ v: SEARCH_SNAPSHOT_VERSION }`，版本不符直接走重建，省一次 loadJSON 失败的异常成本（P3）。

### E. 后台编排 `entrypoints/background.ts`（431 行）

**现状**：消息路由表化 ✓、guardedSync 互斥 ✓、DNR 规则、omnibox 缓存、alarms、contextMenus。

**问题**：
- **E1 · 五种职责同居**：消息路由表、omnibox、DNR、contextMenus/alarms、getBgState。431 行不算失控，但每加一个域（如未来的 Badge/通知）都会继续膨胀。
- **E2 · `getBgState` 手工聚合 6 个来源**（token/login/ghSync/bmSync/meta/indexVersion），每加一个状态字段改一处；且与 `core/msg.ts` 的 BgState 类型定义分离。
- **E3 · omnibox 建议缓存与 classify 无关但同文件**，其失效依赖 storage.onChanged —— 与侧边栏的失效合并器是两套独立逻辑，行为一致性靠约定。

**建议**：
1. 按域拆子模块：`background/handlers.ts`（路由表）、`background/omnibox.ts`、`background/dnr.ts`、`background/lifecycle.ts`（alarms/onInstalled/onStartup），主文件只做组装（P2）。
2. `getBgState` 的字段聚合改为各域自行 `registerStateProvider()`（与消息路由表同风格），BgState 类型随 provider 收拢（P3）。

### F. UI 层 `sidepanel`（App 813 + components）与 `options`（App 955 行）

**现状**：sidepanel 已拆 7 组件（App 从 1582→813）；options 仍是巨石（R1 遗留）；侧边栏已监听 ui 偏好实时同步。

**问题**：
- **F1 · options/App.tsx 955 行 ≈ 10 个面板**（Token/同步/AI/规则/导出/健康/诊断/数据清除/语言/主题）挤在一个文件，每个面板各自 state + 函数，新增面板继续膨胀。
- **F2 · sidepanel/App.tsx 仍有 813 行**：主逻辑 + trending 状态机 + 批量选择 + invalidate 合并器。components 只拆了**叶子展示组件**，"trending 加载/暂停/刷新"这类状态机还留在 App。
- **F3 · UI 层轮询节奏硬编码**：`setInterval(2000)` 在 options 出现 3 处（AI/classify/同步）、sidepanel 2 处——轮询结束条件与展示各写各的。
- **F4 · `dangerouslySetInnerHTML`** 只在 ResultCard 标题（highlight 已转义 ✓）——保持单一入口即可，新增富文本渲染必须复用 `highlight()`。
- **F5 · 侧边栏/设置页对"worker 数据"存在双通道**：消息（search/tree）与页面直读 Dexie（exportCurrent/健康报告）并存——直读路径绕过 worker 缓存，大库下每次全表加载。

**建议**：
1. options 按 panel 拆分：`options/panels/{Token,Sync,Ai,Rules,Export,Health,Diag,Data}.tsx` + `usePanelMsg()` 小工具；App.tsx 只剩布局与全局 state（P1，最大的一块技术债）。
2. sidepanel 抽 `sidepanel/hooks/useTrending.ts`（加载/周期/缓存状态机）与 `useInvalidateBatch.ts`（失效合并器，已有测试友好的纯逻辑）（P2）。
3. 轮询统一 `usePolling(fn, intervalMs, stopWhen)` hook，interval 收敛到 constants（P3）。
4. 双通道原则写进架构文档：**读 worker 已缓存的数据走消息；一次性低频导出/报表允许直读 Dexie**——现状符合该原则，落成文字即可（P3，纯文档）。

### 3.2 性能优化机会（按收益排序）

1. **P2 · options 健康报告缓存**：`refresh()` 每次全表 `allItems()` + `buildHealthReport`（O(n) + 标题归一），设置页每次打开/手动刷新触发。建议：挂 `indexVersion` 缓存（同 worker 模式），版本不变直接复用报告。
2. **P2 · doSearch 的 bulkGet 补齐**：每次按键（防抖后）对命中条目 `bulkGet` 补 description——60 条/次可接受，但可与 worker 条目缓存合并（缓存里已有完整 StarItem，`itemToHit` 直接带 description，省掉整段 bulkGet）。
3. **P3 · `getItemsCached` 的浅拷贝**：`applyPatch` 后 `[...byId.values()]` 全量重建数组——万级条目下每次 patch O(n)。改用 `Map` 作为缓存本体（读时 `[...map.values()]` 仅在 doSearch 需要）。
4. **P3 · `stripSourceForUrls` / `reconcileStars` 全表过滤**：`sources` 数组无法索引（IndexedDB 不支持数组键）——数据量到 5w+ 时考虑影子列 `hasStar: 1`（隐藏索引已存在 hidden 索引，同法可加）。
5. **P3 · BuildFolderTree 每次标签变更全量重建**：已有缓存，重建本身 O(n)——观察即可，暂不动。
