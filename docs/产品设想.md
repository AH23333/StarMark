# 产品介绍文档 & 技术可行性分析

**项目代号：StarMark**（暂定）


## 一、产品定位

### 1.1 一句话描述

一款浏览器扩展，将 GitHub Stars 与浏览器书签整合为统一的本地搜索入口，让用户像查找书签一样快速定位 Star 过的项目。

### 1.2 目标用户

- 有 100+ GitHub Stars、日常用浏览器书签收藏技术资料的开发者
- 痛点：Stars 只进不出，找项目靠翻 GitHub 原生页面；书签和 Stars 是两个孤岛

### 1.3 核心场景

| 场景 | 当前做法 | 目标做法 |
|------|---------|---------|
| 找上周 Star 的一个 RAG 工具 | 打开 GitHub → Stars → 翻页 → 手动搜 | 快捷键唤起 → 输入关键词 → 书签和 Stars 结果混排 |
| 找一个收藏过的技术文档 | 浏览器书签栏翻文件夹 | 同一个搜索框，输入关键词即可 |
| 回忆“当初为什么 Star 这个项目” | 无法实现 | 查看收藏时记录的备注 |

### 1.4 产品形态决策

**选择浏览器扩展（Manifest V3），不选独立应用。** 理由：

- 书签 API 仅浏览器扩展可访问，Web 应用无法直接读取
- 用户 Star 行为发生在 GitHub 页面，扩展可以零迁移成本接入
- 独立应用需要用户主动打开，违背“像查书签一样快”的核心诉求

### 1.5 功能范围（MVP）

**做：**
- 通过 GitHub PAT 拉取用户 Stars 列表，本地缓存
- 读取浏览器书签树，建立本地索引
- 侧边栏 + 地址栏统一搜索（书签 + Stars 混排）
- 结果卡片区分来源（书签显示域名，Star 显示仓库名 + 语言）

**暂不做：**
- AI 分类/自动标签（后续版本）
- 收藏理由记录（后续版本）
- 跨设备同步（后续版本）
- 语义搜索/向量嵌入（后续版本）


## 二、技术可行性分析

### 2.1 数据获取层

#### 2.1.1 GitHub Stars 数据

**方案：Personal Access Token (PAT)**

使用 Classic PAT，仅需 `public_repo` 权限即可读取用户的 starred 仓库列表。通过 `GET /user/starred?per_page=100` 分页拉取。

**关键约束：**

| 约束项 | 具体数值 | 影响 |
|--------|---------|------|
| 认证用户 API 速率限制 | 5,000 请求/小时 | 按每页 100 条计算，500 个 Star 需要 5 次请求，完全在限制内 |
| 单个仓库 stargazers 分页 | 100 条/页 | 我们只拉用户的 starred 列表，不拉仓库的 stargazers，不受此限制 |
| Search API 结果上限 | 1,000 条 | 不涉及，我们使用 `/user/starred` 而非 Search API |

**必须面对的工程问题：**

- **Token 存储安全**：`chrome.storage.local` 中的 PAT 是明文存储的。扩展的 storage 比 localStorage 稍安全，但并非加密存储。对于纯本地工具，这是可接受的权衡，但需要在隐私政策中明确说明。
- **OAuth 的替代方案**：GitHub OAuth 需要 `chrome.identity.launchWebAuthFlow` + 服务端交换 token（因为 client secret 不能放在扩展源码中）。这意味着需要部署一个 Serverless 函数，增加了运维成本和隐私争议（用户数据经过你的服务器）。**MVP 阶段建议先用 PAT，OAuth 作为后续选项。**

#### 2.1.2 浏览器书签数据

**方案：`chrome.bookmarks` API**

在 `manifest.json` 中声明 `bookmarks` 权限即可读取书签树。

**关键约束：**

| 约束项 | 具体情况 | 影响 |
|--------|---------|------|
| `getTree()` 性能 | 递归返回全部节点，10,000 条书签会一次性返回所有数据 | 首次加载可能阻塞主线程，需要异步处理 |
| 根节点 ID 不一致 | Chrome 用 `"0"`，Firefox 用 `"root________"` | 跨浏览器适配需要处理 |
| 缺少 `ROOT_NODE_ID` 常量 | 截至 2026 年初仍在提案阶段 | 需要硬编码或通过 `getTree()` 解析 |
| 权限警告 | 安装时显示“读取和更改您的书签” | 可能影响安装转化率 |

**必须面对的工程问题：**

- **书签数量规模差异极大**：轻度用户可能只有几十个书签，重度用户可能有 5,000-10,000+ 个。`getTree()` 在 ~3,000 个书签时已经可能出现 UI 卡顿。需要采用 `getChildren(id)` 逐层遍历替代一次性 `getTree()`，但需要知道根节点 ID。
- **书签变更监听**：`chrome.bookmarks.onCreated` / `onRemoved` / `onChanged` 事件需要在 Background Service Worker 中处理，但 MV3 的 Service Worker 是非持久化的，事件监听器可能被随时终止。需要设计基于事件的轻量同步机制，而非依赖长驻状态。

### 2.2 数据存储与索引层

#### 2.2.1 存储方案

**方案：IndexedDB（通过 Dexie.js）**

IndexedDB 突破了 localStorage 的 5MB 限制，适合存储大量仓库元数据和书签记录。Better GitHub Stars Manager 等同类工具均采用此方案，验证了可行性。

**数据结构设计（草案）：**

```
表: items
  id: string (URL 的 hash)
  type: 'star' | 'bookmark'
  url: string
  title: string
  description: string
  source: 'github' | 'bookmark'
  metadata: JSON  // Star 额外存 language, stars, topics; 书签存 folderPath
  createdAt: number
  updatedAt: number
```

#### 2.2.2 搜索方案

**方案：MiniSearch（全文索引）**

MiniSearch 是一个轻量级全文搜索库，支持索引序列化和持久化，在 IndexedDB 中存储索引可实现快速加载。对于 10,000 条文档规模，MiniSearch 在浏览器环境中表现良好。

**需要诚实面对的性能问题：**

- **索引构建时间**：首次加载时构建 10,000 条文档的索引，在中等性能设备上预计需要 1-3 秒。可通过 Web Worker 在后台构建，避免阻塞 UI。
- **索引更新**：当用户新增 Star 或书签时，需要增量更新索引。MiniSearch 支持 `add` / `remove` 单条操作，但频繁触发需要节流策略。
- **搜索延迟**：索引构建完成后，搜索本身在毫秒级。真正的瓶颈在索引构建和存储 I/O，不在查询。

### 2.3 统一搜索层

**技术方案：并行搜索 + 结果融合**

在侧边栏或地址栏中，同时调用书签索引和 Stars 索引的搜索，将结果按相关性混排。My-Hub 扩展已经实现了“并行检索浏览历史与书签，结果合并展示”的模式，可作为参考实现。

**需要处理的问题：**

- **相关性排序**：书签和 Stars 的搜索结果如何混排？是按搜索分数统一排序，还是分组展示？分组展示对用户更友好，但增加了 UI 复杂度。
- **结果去重**：用户可能同时 Star 了一个仓库并将其添加为书签。需要按 URL 去重，但保留两种来源标记。

### 2.4 扩展架构

**技术栈：** WXT（扩展框架） + TypeScript + React + Dexie.js + MiniSearch

**MV3 架构约束：**

Manifest V3 的 Service Worker 是非持久化的，会被浏览器随时终止。这意味着：

- 不能在内存中保存长期状态（如全量索引）
- 所有状态必须持久化到 IndexedDB 或 `chrome.storage`
- 事件监听器需要在每次 Service Worker 唤醒时重新注册
- 长任务需要拆分为可恢复的步骤，参考 Better GitHub Stars Manager 的 `OrganizedJob` 状态机设计

**权限清单：**

| 权限 | 用途 | 必要性 |
|------|------|--------|
| `bookmarks` | 读取书签树 | 核心功能 |
| `storage` | 存储偏好和 token | 核心功能 |
| `sidePanel` | 侧边栏展示搜索界面 | 核心功能 |
| `alarms` | 定时同步 Stars | 可选，用于后台定期刷新 |

### 2.5 跨浏览器兼容性

| 浏览器 | 书签 API | Side Panel | 备注 |
|--------|---------|------------|------|
| Chrome | ✅ | ✅ `chrome.sidePanel` | 主目标平台 |
| Edge | ✅ | ✅ | Chromium 内核，兼容 |
| Firefox | ✅ | ❌ 无 Side Panel | 需用 Popup 替代；Service Worker 模型不同 |

**MVP 建议先只做 Chrome/Edge，Firefox 作为后续适配。**


## 三、客观风险评估

### 3.1 高风险项

**风险 1：书签 API 的性能天花板**

`getTree()` 在数千条书签时就有性能问题，而 `getChildren()` 需要知道根节点 ID。Chrome 和 Firefox 的根节点 ID 不一致，且标准提案（W3C WebExtensions #847）截至 2026 年初尚未落地。这意味着你需要维护一套跨浏览器的根节点适配逻辑，且无法保证未来 API 变更的兼容性。

**风险 2：MV3 Service Worker 的生命周期管理**

这是所有 MV3 扩展的共性问题。Service Worker 可能在任意时刻被终止，如果同步逻辑依赖于内存中的状态，会导致数据不一致或重复请求。Better GitHub Stars Manager 用持久化状态机（`OrganizedJob`）来解决，但这增加了显著的架构复杂度。

**风险 3：Chrome Web Store 审核**

`bookmarks` 权限会触发明确的用户警告：“读取和更改您的书签”。审核团队会重点审查：为什么需要这个权限、数据是否上传、是否有隐私政策。如果隐私政策说明不到位，可能被拒绝或延迟上架。

### 3.2 中等风险项

**风险 4：用户数据规模的不确定性**

Star 数量从几十到几千不等，书签数量从几百到上万不等。搜索索引的性能在 1,000 条和 10,000 条之间的差异是非线性的。需要在真实用户数据上做性能测试，而非依赖开发者的干净数据集。

**风险 5：跨设备同步的缺失**

MVP 阶段数据完全本地化，意味着换设备或重装浏览器后需要重新同步。用户可能期望“我在手机上 Star 的项目，在电脑上也能搜到”——但这是 MVP 明确不解决的问题。

**风险 6：搜索的“足够好”标准**

用户在浏览器地址栏搜索时，期望的是**即时反馈**。如果索引构建耗时超过 500ms，用户体验就会打折扣。而书签数据的初始加载 + Stars 的首次同步 + 索引构建，这三步串行执行的总时间可能在数秒级别。

### 3.3 低风险但需关注项

- **GitHub API 变更**：GitHub REST API 相对稳定，但 `/user/starred` 端点未来可能迁移到 GraphQL。当前 REST 版本仍可用。
- **PAT 过期**：Classic PAT 可以设置为永不过期，但 GitHub 正在推动细粒度 token。需要在设置页引导用户创建合适的 token。
- **书签栏/其他书签的根节点识别**：Chrome 的 `"1"` 和 `"2"` 分别对应书签栏和其他书签，但这些 ID 并非正式 API 文档的一部分，依赖它们存在风险。


## 四、分阶段可行性判断

| 阶段 | 功能 | 可行性 | 主要挑战 |
|------|------|--------|---------|
| Phase 1（MVP） | 本地搜索 Stars + 书签 | **高** | 书签 API 性能、索引构建时间 |
| Phase 2 | AI 分类/摘要 | **中高** | 调用 LLM 的成本和隐私；用户需要配置 API Key |
| Phase 3 | 语义搜索 | **中** | 需要本地嵌入模型或云端 API；索引体积增大 |
| Phase 4 | 跨设备同步 | **中低** | 需要自建后端或依赖 Gist；加密存储的实现复杂度 |
| Phase 5 | 收藏理由/笔记 | **高** | 技术简单，但需要用户有记录习惯，否则数据为空 |

**核心结论：MVP 在技术上完全可行，但“像查书签一样快”的体验需要认真解决三个工程问题——书签树的异步加载、索引的增量维护、MV3 Service Worker 的状态管理。** 这三者都不是不可逾越的技术障碍，但都是需要投入工程精力打磨的细节。


## 五、竞品参考

| 产品 | 覆盖范围 | 形态 | 与本产品的差异 |
|------|---------|------|----------------|
| Better GitHub Stars Manager | 仅 Stars | 扩展 | 不涉及书签；功能更重（AI 分类、Watch 管理） |
| My-Hub | 书签 + 历史 | 扩展 | 不涉及 Stars；已有统一搜索实现可供参考 |
| LD-Notion Hub | Stars + 书签 + 论坛 | 脚本 + 扩展 | 依赖 Notion，重量级，非日常搜索工具 |
| Karakeep | 书签 + 笔记 + 文件 | 自托管 Web | 26.9k Star，但不支持 GitHub Stars 集成 |

**差异化定位：不做“管理面板”，做“搜索入口”。** 现有工具都在做更好的分类、标签、笔记界面，但用户的日常行为是**查找**，不是整理。统一搜索框是最轻量的交互形态，也是现有产品都没有认真做好的部分。
