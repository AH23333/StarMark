## §1 存储层（`src/core/db.ts`）

### 1.1 数据库 Schema（Dexie，库名 `starmark`，4 个版本）

| 表 | 主键/索引 | 内容 | 类比 |
|---|---|---|---|
| `items` | `id`（URL 哈希）、`&url` 唯一、`starredAt/bookmarkedAt/updatedAt/hidden` | 全部收藏条目（Star+书签合并行） | 主业务表 |
| `searchIndex` | `id='main'` 单行 | MiniSearch 快照（deflate 压缩 Blob）+ version | 索引持久化文件 |
| `syncState` | `key` | 各种检查点：`gh.sync`、`bm.sync`、`ai.pipeline.state`、`ai.classify.state` | 作业调度表 |
| `activity` | 自增 `++id`、`at` 索引 | 动态事件（star/bookmark 加/删），上限 500 条 | 事件日志表 |
| `meta` | `key='app'` 单行 | 聚合计数缓存 `AppMeta`（total/stars/bookmarks/hidden/tagged/tags 直方图） | 物化视图 |
| `suggestions` | `id=itemId|tag`、`status`、`itemId`、`tag` | AI 建议桶（pending→approved/rejected） | 审批暂存表 |

### 1.2 写入合并：`upsertItems` 与 `mergePreserving`（db.ts:161-193）

所有来源（同步/导入/转换）写条目都走这一个口子，分块 500 条、单事务：

```
incoming（来源侧权威的字段：title/description/starMeta/folderPaths...）
    +
old（库里已有行）
    ↓ mergePreserving
merged = { ...incoming,
           tags/notes/summary/hidden/embedded/createdAt ← 保留旧值（用户字段）,
           updatedAt ← 内容字段有变化才刷新 }
```

`contentChanged()`（db.ts:143）决定 `updatedAt` 是否刷新——保证"再同步一次"不会把浏览排序打乱。**已知缺陷**：review 字段不在保留清单（审查报告 P0-2）；`upsertItems` 的 meta 增量在 `restoreBackup` 场景会翻倍（P0-1）。

### 1.3 meta 增量计数（db.ts:84-116）

`applyItemDelta(meta, old, next)` 对单行的前后状态做差分：来源增减、hidden 翻转、每个标签 ±1。所有批量操作（`stripSourceForUrls`/`updateItem`/`applyBatch`/`transformItems`）都在各自事务内"取 meta → 逐行 delta → 写回 meta"，保证计数与数据强一致（单事务内）。

### 1.4 来源摘除：`stripSourceForUrls`（db.ts:211-232）

删除某个来源（如用户取消了 Star）：`sources` 数组移除该来源；**若 sources 清空则整行删除**。这是"同一 URL 双来源合并"模型的配套删除语义。

### 1.5 批量操作（db.ts:266-364）

`applyBatch` 支持批量加/删标签、隐藏、删除。删除时会**连带删除真实浏览器书签**（按 URL 在书签树中查找匹配节点逐个 remove），这会触发 `onRemoved` 增量事件回流（幂等：来源已摘除，再次 strip 是空操作）。

## §2 索引与搜索（`entrypoints/sidepanel/search-worker.ts` + `core/search/indexer.ts`）

### 2.1 为什么有 Worker、为什么有快照

MiniSearch 是纯内存倒排索引。5000 条目全量重建约几百毫秒——不能在 UI 线程跑（会卡输入），所以放进 Web Worker；又不能每次开面板都重建（IndexedDB 全表读 + 分词太慢），所以序列化压缩成快照存 `searchIndex` 表，启动时优先加载快照。

### 2.2 索引结构（indexer.ts）

- **索引字段**：title、url、description、owner、topics、tags、notes
- **storeFields**（命中后直接随行返回的小字段）：id/url/title/sources/tags/language/stars/时间戳/hidden/favicon——注意故意**不含** description/notes（省内存），命中后按 id 从 DB 补取（worker 224-231 行）
- **CJK 分词器**（indexer.ts:28-44）：拉丁词保持整词；中文段落输出 `整串 + 单字 + 相邻二元组`。例如"搜索工具" → `搜索工具 / 搜 / 索 / 索搜 / 搜索 / 索工 / 工具 / 工 / 具`。这使得中文前缀与包含检索都能命中，代价是索引体积约为原文 2-3 倍。

### 2.3 Worker 的生命周期与串行化

```
侧边栏打开 → postMessage({type:'init', version})
    → ensureIndex: 快照存在且 version 匹配？ → 反序列化（解压）
                  否则 → allItems() 全量重建 → 压缩落快照
    → postMessage({type:'ready'})
```

- 所有操作（init/invalidate/search）进**单 Promise 链**（worker:14-20），保证"读改写索引"不交错。
- 增量补丁 `applyPatch(ids)`（worker:42-62）：`bulkGet` 取最新行 → 逐条 `discard + add`；id 数超过索引文档数一半时直接全量重建更划算。
- 持久化防抖 4 秒（worker:22-40）：连续增量只落一次盘；写失败不影响搜索（下次 init 会全量重建兜底）。

### 2.4 查询路径 `doSearch`（worker:150-234）

```
q = ""（浏览模式）          → allItems 过滤(隐藏/来源/标签AND) → 排序 → 前 max 条
q 非空：
  ① MiniSearch.search(前缀+模糊0.2) 按相关度取命中
  ② 命中不足 max → 全表字面兜底（title/url 包含匹配）     ← 性能点，见审查 P2-2
  ③ storeFields 缺的大字段按 id bulkGet 补齐
  返回 { items, total }（total=本次返回数，非命中总数）
```

排序在两处发生：worker `sortItems`（非相关度排序时）与前端 `selectors.groupHits`（relevance 模式分"精确/相关"两组）——语义重复，属重构点（审查 R2）。

## §3 GitHub 同步（`core/sync/github.ts` + `api/github.ts`）

### 3.1 触发点

| 触发 | 位置 |
|---|---|
| 定时闹钟（默认 6h，最低 30min） | `alarms.onAlarm`（background:45-47） |
| 浏览器启动 / 扩展安装 | onStartup / onInstalled |
| 设置页「保存并同步」/ 侧边栏「同步」按钮 / PAT 变更 | 消息 `run-sync`、storage.onChanged |

侧边栏按钮路径还有 `syncRunning` 会话内互斥（background:25,288-300）。

### 3.2 状态机（检查点持久化在 `syncState['gh.sync']`）

```
VALIDATE ──token 有效──▶ FETCH_PAGES ──分页拉完──▶ RECONCILE ──▶ TAG_INDEX ──▶ DONE
   │ 401→AUTH_ERROR          │ 每页: repoToItem→upsertItems      │ 对账删除       │ 仅 bump 版本
   │                         │       记录 seenUrls + 新Star动态    │              │
   └──────── 每阶段落检查点，SW 被杀 → 下次从 checkpoint.phase 续跑 ─────────┘
```

关键细节：

- **分页停止条件**：跨域读不到 Link 头，用"满页（≥100条）即可能还有下一页"的长度启发式，空页自然停（api/github.ts:59-106）。上限 200 页（2 万条）。
- **304 短路**：DONE 状态下再次同步，从第 1 页携带上轮 etag，命中 304 直接 `NOT_MODIFIED` 结束。**已知缺陷**：etag 保存/使用方式使增量实际失效，退化为全量爬取（审查 P1-2）。
- **RECONCILE 对账**：`seenUrls`（本轮内存集合）之外的 star 来源全部摘除——处理"用户取消 Star"。集合在内存，SW 中途被杀则下轮重新 FETCH，幂等安全。
- **完成后**：`finish()` 置 DONE + fire-and-forget `applyRulesToAll()`（自动规则标签，失败不影响同步结果）。
- **活动记录**：新 Star → `star_add` 动态；对账删除 → `star_remove`。

### 3.3 API 客户端要点（api/github.ts）

- 统一错误类型 `GitHubApiError(status, msg, retryAfterMs)`；401=Token 失效、403/429=限流（解析 Retry-After 但同步层未利用，审查 P2-5）。
- `starRepo`（PUT starred）与 `getRepo` 供"书签 → Star"转换（convert.ts）使用。

## §4 书签同步（`core/sync/bookmarks.ts`）

### 4.1 全量遍历 `walkAllBookmarks`（触发：安装/启动/10分钟节流/1小时兜底）

```
bookmarks.getTree()
  → 从各根 BFS：getChildren(id) 逐层展开
  → 每个 URL 书签：bookmarkToItem(node, 目录路径链, 目录id链)
  → upsertBookmark：已有行→并入 bookmark 来源；否则新行
  → bumpIndexVersion()
```

目录路径 = 从根到父文件夹的标题链，是收藏夹树视图的数据来源。**已知问题**：逐条 `getByUrl + 单行事务`（N+1，审查 P2-1）；`lastFullWalkAt` 在遍历**开始**就写入，SW 中途被杀会留下半截数据且 10 分钟内不会重走。

### 4.2 增量事件（1 秒防抖队列）

```
onCreated ──▶ {created, node}   ──▶ folderPathFor(parentId) 即时回溯路径 → upsert → 规则标签
onRemoved ──▶ {removed, url}    ──▶ stripSourceForUrls(['bookmark'])（可能只是摘源）
onChanged/onMoved ─▶ {changedOrMoved, id} ─▶ get(id) → upsert（⚠ 路径用 [''] 占位，审查 P1-7）
```

设计意图：浏览器书签是**事实源**，扩展只镜像入库。删除/移动/改名都靠事件流增量维护；SW 死亡期间丢的事件由 1 小时兜底全量对账补齐。

## §5 变更通知总线：indexVersion + idxPatch（`core/version.ts`）

这是连接"数据变了"与"搜索索引更新"的机制，理解它就理解了全项目的联动：

```
任何数据写入（同步/编辑/批量/规则/AI应用）
    → bumpIndexVersion(ids?)        # storage.local: indexVersion++ 且 idxPatch={seq,ids|null}
                                     # ids=null=全量重建；ids=[]=仅版本变化；[...]=增量补丁
    → 侧边栏的 storage.onChanged 监听（App.tsx:113-134）
        → 500ms 防抖
        → worker.postMessage({type:'invalidate', ids, version})
        → 同步刷新 树/标签/计数
    → worker applyPatch(ids) 或全量重建 → 广播 ready → 界面用新索引重跑当前查询
```

三类 invalidation 语义：**null** 全量（恢复备份/清空）、**[]** 仅状态（TAG_INDEX 恢复进度）、**[ids]** 增量（绝大多数）。Worker 收到 ids 过半则自行升级为全量。**已知缺陷**：bump 的读改写无串行化，并发可丢补丁（审查 P1-3）。

## §7 前端两页面

### 7.1 侧边栏（App.tsx，1581 行）

- **状态**：query/hits/tab/prefs/tagFilters/tree/activity/hiddenItems 等 ~15 个 useState；UIPrefs 持久化在 storage.local `ui`。
- **数据获取**：全部经 Worker（搜索/树/标签/动态/隐藏）或 SW（同步/编辑），自身不碰 IndexedDB。
- **搜索流**：query 变化 → 120ms 防抖 → `{type:'search', q, source, includeHidden, sort, tags}` → hits → `groupHits` 分组（域名分组 / 单组排序 / 精确+相关两段）→ 渲染。
- **视图**：非搜索态显示四个 tab——📁 收藏夹树（BrowseNode 递归，每节点默认 100 条 + 展开更多）、🏷 标签云（点击 AND 叠加过滤）、🕒 动态、🙈 隐藏；有搜索词时 tab 隐藏、专注结果。
- **卡片能力**：打开/高亮命中/标签芯片（点击即按标签过滤）/行内编辑笔记标签/隐藏/右键菜单（项可配置）。
- **去重提示**：同归一化标题多条 → 黄色 dup 徽章。

### 7.2 设置页（options/App.tsx，952 行）

分区：GitHub 连接（PAT 保存即校验+同步）→ 概览与健康报告（insights：健康分/重复组/语言分布/趋势）→ 规则管理 → 标签批量操作 → AI 建议/分类 → 备份导出导入 → 数据清理 → 语言/快捷键/右键菜单开关。

## §8 AI 子系统（全部 BYOK，默认关闭）

| 模块 | 输入 | 产物 | 安全机制 |
|---|---|---|---|
| `provider.ts` | OpenAI/Anthropic/Ollama 设置（`ai.settings`） | 统一 chat(JSON) 接口 | Key 只存本地 |
| `pipeline.ts` 建议流水线 | 全库条目分批送模型 | `suggestions` 表 pending 建议 | **建议桶**：用户批准才并入 tags；检查点 cursor 续跑 |
| `classify.ts` 批量分类 | 现有标签频次作参考类别（防过细/过粗） | storage.local 分类结果（tag→ids） | 每批落检查点、可暂停/心跳判僵尸；应用走 updateItem 追加；可导出/导入 |

两者的共同模式：**检查点状态机 + 幂等续跑 + 人工确认闸门**，与 GitHub 同步同构。

## §9 周边能力速览

- **rules.ts**：用户规则（domain/url/title/language 匹配 → 追加标签），存 `tagRules`；同步成功与新书签自动应用；追加式幂等。
- **activity.ts**：动态表，写入时超 500 修剪最旧。
- **backup.ts**：明文 JSON 或 AES-256-GCM（PBKDF2 100k、随机 salt/IV）信封；恢复=清 items 重建（审查 P0-1）。
- **export.ts / convert.ts / trending.ts / insights.ts**：导出三格式；Star↔书签互转（写「StarMark 收藏」夹或 starRepo）；热榜抓取 github.com/trending（失败回退 Search API）；健康报告。

## §10 两个完整时序（把所有子系统串起来）

### 时序 A：用户点「同步」按钮

```
SidePanel            Background SW                GitHub API        IndexedDB          Worker
   │ run-sync ──────────▶ │                            │                │                │
   │                      │ syncRunning=true            │                │                │
   │                      │ VALIDATE: /user ───────────▶ │                │                │
   │                      │ FETCH_PAGES: /user/starred▶ │（每页 upsert ──▶ │ items+meta）   │
   │                      │   checkpoint 每页落盘        │                │                │
   │                      │ RECONCILE: 摘除取消的Star ──────────────────▶ │ stripSource    │
   │                      │ bumpIndexVersion(changedIds) ── storage.local ──────────────▶ │(onChanged
   │                      │ DONE；applyRulesToAll（规则追加标签→又一次bump）               │  500ms防抖)
   │ ◀─── sendResponse ── │                            │                │  invalidate ──▶ │ applyPatch
   │ setHits(新查询) ◀──────────────── results ◀──────────────────────────────────────────── │ ready
```

### 时序 B：编辑一条的标签

```
SidePanel ─ update-item{id,patch} ─▶ SW.updateItem（事务：行+meta）─▶ bumpIndexVersion([id])
                                                                       │
   SidePanel storage.onChanged ◀───────────────────────────────────────┘
        ├─ worker.invalidate([id]) → discard+add → ready → 重跑当前查询
        └─ 树/标签计数刷新
```
